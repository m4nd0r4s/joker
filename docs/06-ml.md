# 06 — ML

> **Scope:** this document describes **v1.1** (ADR 0019). v1 does not include ML, but it reserves everything ML needs (document 11, "Prepared for ML").

ML is a **runtime resource**, like a device. Apps do not link ML libraries: they declare a model port and request inferences, or they consume the outputs of native pipelines. The runtime chooses the backend, manages the accelerator, enforces deadlines, detects out-of-distribution inputs and records whatever is needed to replay.

Section 12 answers the question "Burn as the backend?".

---

## 1. Principles

1. **A model is declared, not embedded.** A `.jkm` artifact with a tensor signature, bound to an app port or to a pipeline.
2. **Backends are plugins behind a trait.** Burn by default, and ORT, HailoRT and TensorRT when the hardware calls for it.
3. **Bulk data does not go through Wasm memory.** Frames and waveforms go through native pipelines to the accelerator (M5).
4. **A model that actuates always goes through shadow mode** before it takes effect (M16, ADR 0012).
5. **The model is not trusted.** Inputs are guarded (M17), outputs are limited by the envelope, and whatever is nondeterministic is recorded (M22).

## 2. The `.jkm` artifact

A `.jkm` is a tar with zstd, signed in **COSE_Sign1** (ref/00 §7, ADR 0025), like all signed documents:

```
load-tcn-v3.jkm
  model.toml            model manifest
  signature.sig         COSE_Sign1 (EdDSA, role `models`) over the hash of everything
  lineage.toml          M10: data, code, metrics
  payload/
    burn/               arch = "joker.tcn@2", weights.bpk (burnpack)
    onnx/model.onnx     (optional) for ORT/tract
    hailo/model.hef     (optional) compiled offline for Hailo-8/8L
    wasm/model.wasm     (optional) model as a Wasm component (§3.4)
```

```toml
# model.toml
[model]
name    = "load-tcn"
version = "3.0.1"
task    = "regression"

[[inputs]]
name   = "history"
dtype  = "f32"
shape  = [1, 96, 4]             # batch, 15 min steps, features
layout = "NTC"
features = ["load_kw", "pv_kw", "temp_c", "is_workday"]

[[outputs]]
name  = "forecast"
dtype = "f32"
shape = [1, 96]
unit  = "kW"

[guard]                          # M17
per_feature = [
  { name = "load_kw", min = 0.0,   max = 2000.0, mean = 310.0, std = 120.0 },
  { name = "pv_kw",   min = 0.0,   max = 400.0 },
  { name = "temp_c",  min = -25.0, max = 45.0 },
]
ood = { method = "zscore", threshold = 4.0, fraction = 0.05 }   # >5% of values with |z|>4 → OOD

[runtime]
deterministic = "cpu-only"       # true | false | "cpu-only"
```

## 3. Four ways to bring a model to the device

| # | Form | Hot swap | On-device training | Hardware | When |
|---|---|---|---|---|---|
| 1 | **Burn: catalog architecture + weights** | yes (weights only) | **yes** | all Burn backends | in-house models: MLP, CNN-1D, TCN, GRU/LSTM, autoencoders, small transformers |
| 2 | **Burn: generated native (burn-onnx → plugin)** | yes (plugin) | if the architecture allows it | all Burn backends | third-party models with supported operators |
| 3 | **ONNX at runtime (ORT / tract)** | yes | no | CPU, CUDA, TensorRT and OpenVINO via ORT | any ONNX, without recompiling |
| 4 | **Vendor payload** (HEF, TensorRT engine, RKNN) | yes | no | specific NPU | accelerators without Burn support |

### 3.1 Architecture catalog

`jokerd` includes a **versioned catalog of architectures** written in Burn (`joker.mlp@1`, `joker.cnn1d@1`, `joker.tcn@2`, `joker.gru@1`, `joker.ae@1`, `joker.tiny_transformer@1`, `joker.yolo_s@1`…). A type 1 `.jkm` carries only `arch`, hyperparameters and weights. Changing weights does not require new code. This is the most common case at the industrial edge: the same architecture retrained per site or per machine.

### 3.2 Generated native

`jk model build model.onnx --via burn` runs burn-onnx, which converts the ONNX into Rust code on the Burn API, and compiles it as a **plugin** (`cdylib`) with a stable C ABI (`joker-ml-abi`: `jm_create`, `jm_infer`, `jm_destroy`, tensor descriptors). The plugin is signed, loaded with `dlopen` in an `ml` thread or in a `joker-ml-<id>` process, and checked against the ABI version. burn-onnx supports a limited set of operators, and so `jk model build` fails early with the list of missing operators and suggests the ORT route.

### 3.3 ONNX at runtime

Backend `ort` (ONNX Runtime via the `ort` crate, with the available execution providers) or `tract` (pure Rust, CPU). It serves "I have an ONNX and I want it running today".

### 3.4 Model as a Wasm component

For tiny models (anomaly with an MLP, classifiers of a few KB), the `.jkm` may carry a Wasm component compiled with Burn Flex for `wasm32`. It runs in wasmtime like an app, is portable across architectures without recompilation and stays in a sandbox. It uses only the CPU and is slower than native. It is the right format for heterogeneous fleets (document 08, round 5).

## 4. Backends and selection

```rust
pub trait InferenceBackend: Send + Sync + 'static {
    fn id(&self) -> BackendId;                               // "burn:cuda", "ort:tensorrt", "hailo"
    fn probe(&self) -> Vec<DeviceInfo>;                      // at startup and in `jk doctor --ml`
    fn supports(&self, m: &ModelManifest) -> Support;        // Yes | No(reason) | Partial(ops)
    fn load(&self, m: &LoadedArtifact, dev: &DeviceInfo, opts: &LoadOpts) -> Result<Box<dyn Session>>;
}

pub trait Session: Send {
    fn infer(&mut self, inputs: &[TensorView], out: &mut [TensorBuf], deadline: Instant) -> Result<Stats>;
    fn warmup(&mut self, n: u32) -> Result<()>;
}
```

- **Fallback chain:** `backend = ["hailo", "burn:vulkan", "ort:cpu"]`. At startup, the first one that `probe` + `supports` accepts is chosen. At runtime, N consecutive failures or missed deadlines (5 by default) move to the next one, with alarm `ml.<m>.fallback`.
- **Honest accelerator detection:** a Vulkan device that turns out to be `llvmpipe` (software rendering) is refused as a GPU. A GPU shared with the display is marked `shared`.
- **Kernel cache:** the CubeCL backends do autotune and JIT compilation of kernels. The cache goes to `/var/lib/joker/ml-cache/<device>/<version>` and is prewarmed in `warmup` during model installation, and not at the first inference in production. Without this, the first request can take seconds.
- **Concurrency:** each session has `max_inflight` (1 by default on NPU/GPU and N on CPU) and optional micro-batching (`batch = { max = 8, wait = "5ms" }`).
- **Priorities:** requests from pipelines with a short deadline go ahead of requests from async tasks on the same accelerator.
- **Isolation:** `isolation = "process"` runs the session in `joker-ml-<id>`, with tensors in shared memory. It is the option for GPU/NPU drivers that can hang (the supervisor kills and restarts the process).

## 5. Native pipelines (M5)

A pipeline connects a stream (or block signal) to a model and to an output signal or event **without going through Wasm memory**:

```
cam0.frames ──▶ crop ──▶ resize ──▶ normalize ──▶ model(detector) ──▶ nms ──▶ vision.detections (event)
    dmabuf        (CPU NEON or GPU, depending on the model's backend)          └▶ frame ts_src preserved
```

| Category | Operations |
|---|---|
| image | `crop`, `resize` (bilinear/area), `letterbox`, `convert` (NV12/YUYV→RGB), `normalize`, `to_tensor(layout)` |
| signal | `window(n, hop)`, `detrend`, `fft(n, window)`, `bands([…])`, `stats(fields)` (`rms`, `peak`, `crest`, `kurtosis`…), `resample`, `append(signals)` (joins scalar signals to the features) |
| model | `model(name)` |
| output | `nms`, `decode_boxes(anchors)`, `argmax`, `topk`, `threshold`, `softmax`, `to_event(schema)`, `to_signal(field)` (a field of the model output becomes a scalar signal in the pipeline's `to`) |
| control | `every(n)` (1 in every n frames), `when(expr)` (only under a condition), `correlate(with, window)` (associates each frame with the edge of a trigger signal whose `ts_hw` is closest; a frame without an edge or an edge without a frame generates an error event) |

- Each step declares input and output formats, and `jk check` validates the chain (`J0510`).
- **Placement:** if the model runs on GPU, the image steps run on the GPU (CubeCL kernels), and if it runs on Hailo, conversion and resize run on CPU NEON. `jk explain pipeline inspect` shows where each step runs and the estimated latency.
- **Latency budget:** the pipeline declares `deadline`. If a frame does not finish in time, the output is emitted with quality `bad(deadline)` so that the app decides (in the visual inspection case, reject the part).

## 6. Inference from apps

```rust
let y = io.forecast.infer([x]).await?;       // Result<Inference, InferError>
match y.quality.code {
    QualityCode::Good      => use_forecast(&y.outputs[0]),
    QualityCode::Uncertain => fallback_plan(),            // OOD
    QualityCode::Bad       => unreachable!(),             // errors come through Err
}
```

(The full `QualityCode::…` paths are required: `Good =>` alone would be a binding pattern that catches everything.)

- **In v1, this is reserved.** The WIT interface `ml`, the `#[model]` port, `infer` and `Tensor` exist with `@unstable(feature = ml)` in the `joker:runtime` world and behind the `unstable-ml` feature of the Rust SDK (without it, `J-E0718`). A component that imports them is rejected in `mode = "prod"` (`J-E0003`) until 1.1, and in `dev` it is linked to stubs that return `J-E0601`. The planned signatures are in ref/04 §2.9 and §4.15, and for the tier 2 SDKs in ref/05 §20.1; they may change until stabilization.

- Inputs are validated against the signature (dtype and shape) before they go to the backend.
- Tensors up to 1 MiB cross the Wasm boundary with one copy. Above that, `jk check` warns and suggests a pipeline.
- A missed deadline gives `Err(Deadline)`, never an indefinite wait.

## 7. Input guard and fallback controller (M17)

A model trained in summer does not know what to do with −15 °C. The guard in `model.toml` compares each request with the training statistics and marks `Uncertain(OutOfDistribution)` when they leave the range. What to do is the app's decision, but the manifest offers the most common pattern:

```toml
[apps.hvac_rl.fallback]
controller = "app:hvac_rules"        # another app, deterministic, always loaded
when       = "ood_ratio(model:hvac_policy, 15m) > 0.2 || !good(model:hvac_policy)"
```

While `when` is true, the arbiter swaps the levels: the fallback controller takes the model's level, and the model drops to `Shadowed`. Everything is logged (document 08, round 6).

## 8. Determinism and replay (M22)

| Backend | Determinism |
|---|---|
| Burn Flex / CubeCL CPU | deterministic for the same binary and the same CPU flags (to validate: parallel reductions) |
| Burn Vulkan/CUDA, TensorRT | **not guaranteed** (order of reductions, autotune) |
| Hailo | deterministic for the same HEF and firmware (to validate) |

That is why **the outputs of models with `deterministic != true` are recorded in the trace**, and `jk replay` uses the recorded ones by default (`--rerun-models` re-executes and shows the differences). Replay stays exact for the app logic, which is what matters to debug.

## 9. On-device training

Burn trains and infers with the same code, and that allows something ORT/TensorRT do not: **adapting the model to each machine, on site.**

```toml
[training.pump7_baseline]
arch      = "joker.ae@1"
from      = "models/ae-vibration-base.jkm"         # initial weights (optional)
data      = { signals = ["pipe:vib7.features"], window = "7d", where = "machine7.running && !any(alarm.**.active)" }
schedule  = "after: 7d of data; then: weekly"
resources = "ml"
priority  = "idle"                                  # SCHED_IDLE; pauses if the rt/io CPU heats up
budget    = { max_time = "2h", max_memory = "512 MiB" }
checkpoint = "10m"
validate  = { holdout = "20%", metric = "recon_p99", max = 0.08 }
output    = "candidate"                             # never straight to production: goes to shadow (M16)
```

- Training is **preemptible**: it checkpoints, pauses under thermal or CPU pressure and resumes.
- The data comes from the historian and is identified by the interval and by the hash of the segments (lineage, M10).
- The result is a **candidate** `.jkm` that enters shadow and only then is promoted.
- Federated learning (several machines sharing weight deltas) is outside the core. It is possible on top (uplink of signed deltas), but it is not part of the 1.1 design (it is left for v2.x, document 21).

## 10. Shadow and promotion (M16)

```toml
[models.detector.shadow]
candidate = "models/yolo-s-parts-v8.jkm"
until     = { frames = 50000, duration = "48h" }
promote_if = [
  "agreement(detector, candidate) >= 0.98",
  "latency_p99(candidate) <= 30ms",
  "ood_ratio(candidate, 24h) <= 0.01",
]
on_regress = "demote"                    # after promotion: regression KPI → roll back
kpi        = "reject_rate(line) within 20% of baseline(7d)"
```

`jk shadow status detector` shows the agreement, the confusion matrix between the two versions, the latencies and the divergent cases (with recorded frames to review). Promotion may be automatic, when the criteria pass, or manual (`jk shadow promote`).

---

### 10.1 KPI expressions

The promotion and demotion criteria (`promote_if`, `kpi`, `until`) use a grammar **separate** from the expressions of document 02, §10: they are evaluated in `bg`, over the historian and the shadow traces, and accept long windows (up to 30 d). Functions: `agreement(a, b)`, `latency_p50/p99(m)`, `ood_ratio(m, window)`, `false_alarm_rate(m, window)`, `reject_rate(signal)`, `baseline(expr, window)`, `within(x, y, %)`, and the comparison and logical operators. They must not be used in permissives, alarms or `calc`.

## 11. Lineage (M10)

The `lineage.toml` of each `.jkm` records: the origin of the data (dataset hash, or historian intervals and device), the commit of the training code, the hyperparameters, the validation metrics, who signed and, for models trained on the device, the parent `.jkm`. `jk model lineage <m>` shows the tree. It is the answer to the question "which model made this decision, and what data was it trained on?".

## 12. Burn as the backend: analysis

### 12.1 What Burn is today

Burn (Tracel AI, MIT/Apache-2.0) is a tensor library and a deep learning framework in Rust, at version 0.22. The points relevant to Joker:

- **Backends:** CubeCL (CUDA, ROCm, Metal, Vulkan, WebGPU, CPU) with kernel fusion and autodiff; **Flex**, a pure Rust CPU backend that also runs on `wasm32` and in `no_std`. The LibTorch backend is *deprecated* since 0.22.
- **Device selection at runtime:** the current API chooses the `Device` at runtime and allows several backends in the same binary. It fits directly into the fallback chain of §4.
- **Training and inference with the same code**, including on-device personalization.
- **Import:** ONNX via burn-onnx (converted into Rust code; limited set of operators), PyTorch and Safetensors weights via `burn-store`.
- **Remote backend (beta):** run tensors on a server with a GPU through Iroh or WebSocket.
- **Status:** in active development, with explicit warnings of breaking changes. 0.22 changed the record format to *burnpack*.

### 12.2 Why it fits

| Reason | Why it matters at the edge |
|---|---|
| **Pure Rust** | one static binary, simple cross-compilation for aarch64/armv7, no Python and no 1 GB libtorch |
| **Backend portability** | the same model runs on CPU, Vulkan (Intel, AMD, Qualcomm and, to validate, the Pi 5 VideoCore), CUDA (Jetson) and Metal (development on the Mac) |
| **Flex in `no_std`** | it is the same ML engine for the future Joker Micro on MCUs |
| **Flex in Wasm** | small models as portable components (§3.4) |
| **On-device training** | per-machine adaptation (round 3), which no inference-only engine gives |
| **Kernel fusion and JIT** | competitive GPU performance without writing kernels by hand |
| **Same language as Joker** | debugging an inference does not require crossing an FFI boundary with C++ |

### 12.3 Where it falls short

| Limitation | Consequence | Mitigation |
|---|---|---|
| **Does not support NPUs** (Hailo, Coral, RKNN, SoC NPUs) | on an RPi 5 with AI HAT+ or on a RevPi with Hailo, the main accelerator is outside Burn | `hailo` backend (HailoRT) as a plugin, with HEF payload |
| **ONNX with limited operators** | third-party models may not convert | via ORT/tract (§3.3) |
| **ONNX becomes code**, it is not loaded at runtime | a new model requires compiling | catalog + weights (§3.1) for the common case, and plugins (§3.2) for the rest |
| **Pre-1.0, with breaking changes** | upgrading Burn can break artifacts | pin the version per runtime minor; `.jkm` files record the Burn version; migration with `jk model migrate` |
| **On Jetson, TensorRT is faster in INT8** | Burn CUDA may lag in latency | optional `tensorrt` backend; measure before deciding |
| **INT8 quantization still maturing** (to validate) | large models on ARM CPU may be slow | ORT with static quantization as an alternative |
| **GPU determinism not guaranteed** | affects replay | M22 (§8) |
| **Autotune/JIT on the first run** | high latency at startup | persistent cache and warmup (§4) |

### 12.4 Decision (ADR 0009)

**Yes to Burn**, as the **default and reference backend**, and as the "in-house" format for the models Joker trains or adapts. **Not as the exclusive backend:** the `InferenceBackend` trait exists from day one, with ORT as the second backend in Phase 2 and HailoRT as the third, because the most likely target hardware (RPi 5 or RevPi with Hailo) requires it.

### 12.5 Hardware × backend matrix

| Hardware | Burn | Other | Initial recommendation |
|---|---|---|---|
| RPi 4/5, CM4/CM5 (CPU) | Flex, CubeCL CPU | tract, ORT | **Burn** |
| RPi 5 (GPU VideoCore VII, Vulkan 1.2 via Mesa v3dv) | CubeCL Vulkan (**to validate**: extensions, performance) | — | measure; CPU probably wins on small models |
| Hailo-8 / 8L (AI HAT+, M.2) | — | **HailoRT** (HEF) | Hailo for vision; Burn CPU for time series |
| Jetson Orin | CubeCL CUDA | TensorRT, ORT-TRT | Burn by default; TensorRT if the benchmark justifies it |
| x86 + NVIDIA | CubeCL CUDA | TensorRT | Burn |
| x86 Intel iGPU | CubeCL Vulkan | ORT-OpenVINO | measure |
| Coral Edge TPU | — | libedgetpu (plugin X) | only if there is demand |
| Rockchip RK3588 NPU | — | RKNN (plugin X) | only if there is demand |
| MCU (Joker Micro) | Flex `no_std` | — | Burn |
| Mac (development) | CubeCL Metal | — | Burn |

### 12.6 What to validate in 1.1 (exit gates)

1. Latency and memory of `joker.tcn@2`, `joker.ae@1` and `joker.cnn1d@1` on Burn Flex and CubeCL CPU on a CM4 and a CM5, compared with tract and ORT.
2. CubeCL Vulkan on the VideoCore VII: does it work? And does it beat the CPU?
3. Flex determinism across runs and between CM4 and CM5.
4. Training of `joker.ae@1` with 7 days of features (≈ 600 k windows) on a CM5 in less than 2 h, in `SCHED_IDLE`, without affecting the jitter of the `rt` group.
5. burn-onnx: percentage of successful conversion on a set of 20 typical edge models (small YOLOs, MobileNet, EfficientNet-Lite, TCN, LSTM).
6. YOLO-s on Hailo-8L via HailoRT: end-to-end pipeline latency, with zero-copy from the camera.

If point 1 fails by more than 2× compared with ORT, the default CPU backend becomes ORT and Burn is kept for GPU and training. The decision is recorded in an ADR.

## 13. Local LLMs and VLMs

Local language models (via `mistral.rs`, `candle` or `llama.cpp` in a tier X process `joker-llm`) are supported as **model servers**, and not as backends of the control path. An assistant that uses an LLM is an app with `writer.kind = "proposal"` (M18): it may read, explain and propose, but it never writes without human approval (document 08, round 6).
