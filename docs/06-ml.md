# 06 — ML

> **Âmbito:** este documento descreve a **v1.1** (ADR 0019). A v1 não inclui ML, mas reserva tudo o que ele precisa (documento 11, "Preparado para ML").

O ML é um **recurso da runtime**, como um dispositivo. As apps não ligam bibliotecas de ML: declaram uma porta de modelo e pedem inferências, ou consomem as saídas de pipelines nativos. A runtime escolhe o backend, gere o acelerador, aplica deadlines, deteta entradas fora da distribuição e grava o que for preciso para reproduzir.

A secção 12 responde à pergunta "Burn como backend?".

---

## 1. Princípios

1. **Um modelo é declarado, não embutido.** Artefacto `.jkm` com assinatura de tensores, ligado a uma porta de app ou a um pipeline.
2. **Os backends são plugins atrás de um trait.** Burn por omissão, e ORT, HailoRT e TensorRT quando o hardware o pede.
3. **Dados volumosos não passam pela memória Wasm.** Frames e formas de onda vão por pipelines nativos até ao acelerador (M5).
4. **Um modelo que atua passa sempre pelo modo sombra** antes de ter efeito (M16, ADR 0012).
5. **O modelo não é de confiança.** As entradas são guardadas (M17), as saídas são limitadas pelo envelope, e o que é não determinista fica gravado (M22).

## 2. O artefacto `.jkm`

Um `.jkm` é um tar com zstd, assinado em **COSE_Sign1** (ref/00 §7, ADR 0025), como todos os documentos assinados:

```
load-tcn-v3.jkm
  model.toml            manifesto do modelo
  signature.sig         COSE_Sign1 (EdDSA, papel `models`) sobre o hash de tudo
  lineage.toml          M10: dados, código, métricas
  payload/
    burn/               arch = "joker.tcn@2", weights.bpk (burnpack)
    onnx/model.onnx     (opcional) para ORT/tract
    hailo/model.hef     (opcional) compilado offline para Hailo-8/8L
    wasm/model.wasm     (opcional) modelo como componente Wasm (§3.4)
```

```toml
# model.toml
[model]
name    = "load-tcn"
version = "3.0.1"
task    = "regression"

[[inputs]]
name   = "history"
dtype  = "f32"
shape  = [1, 96, 4]             # batch, passos de 15 min, features
layout = "NTC"
features = ["load_kw", "pv_kw", "temp_c", "is_workday"]

[[outputs]]
name  = "forecast"
dtype = "f32"
shape = [1, 96]
unit  = "kW"

[guard]                          # M17
per_feature = [
  { name = "load_kw", min = 0.0,   max = 2000.0, mean = 310.0, std = 120.0 },
  { name = "pv_kw",   min = 0.0,   max = 400.0 },
  { name = "temp_c",  min = -25.0, max = 45.0 },
]
ood = { method = "zscore", threshold = 4.0, fraction = 0.05 }   # >5% dos valores com |z|>4 → OOD

[runtime]
deterministic = "cpu-only"       # true | false | "cpu-only"
```

## 3. Quatro maneiras de levar um modelo ao dispositivo

| # | Forma | Troca a quente | Treino no dispositivo | Hardware | Quando |
|---|---|---|---|---|---|
| 1 | **Burn: arquitetura de catálogo + pesos** | sim (só pesos) | **sim** | todos os backends Burn | modelos da casa: MLP, CNN-1D, TCN, GRU/LSTM, autoencoders, transformers pequenos |
| 2 | **Burn: nativo gerado (burn-onnx → plugin)** | sim (plugin) | se a arquitetura o permitir | todos os backends Burn | modelos de terceiros com operadores suportados |
| 3 | **ONNX em runtime (ORT / tract)** | sim | não | CPU, CUDA, TensorRT e OpenVINO via ORT | qualquer ONNX, sem recompilar |
| 4 | **Payload de fabricante** (HEF, engine TensorRT, RKNN) | sim | não | NPU específica | aceleradores sem suporte Burn |

### 3.1 Catálogo de arquiteturas

O `jokerd` inclui um **catálogo versionado de arquiteturas** escritas em Burn (`joker.mlp@1`, `joker.cnn1d@1`, `joker.tcn@2`, `joker.gru@1`, `joker.ae@1`, `joker.tiny_transformer@1`, `joker.yolo_s@1`…). Um `.jkm` do tipo 1 traz apenas `arch`, hiperparâmetros e pesos. Mudar de pesos não exige código novo. É o caso mais comum no edge industrial: a mesma arquitetura retreinada por site ou por máquina.

### 3.2 Nativo gerado

`jk model build model.onnx --via burn` corre o burn-onnx, que converte o ONNX em código Rust sobre a API Burn, e compila-o como **plugin** (`cdylib`) com uma ABI C estável (`joker-ml-abi`: `jm_create`, `jm_infer`, `jm_destroy`, descritores de tensores). O plugin é assinado, carregado com `dlopen` numa thread `ml` ou num processo `joker-ml-<id>`, e verificado contra a versão da ABI. O burn-onnx suporta um conjunto limitado de operadores, e por isso o `jk model build` falha cedo com a lista dos operadores em falta e sugere a via ORT.

### 3.3 ONNX em runtime

Backend `ort` (ONNX Runtime via o crate `ort`, com os execution providers disponíveis) ou `tract` (puro Rust, CPU). Serve para "tenho um ONNX e quero que corra hoje".

### 3.4 Modelo como componente Wasm

Para modelos minúsculos (anomalia com MLP, classificadores de poucos KB), o `.jkm` pode trazer um componente Wasm compilado com Burn Flex para `wasm32`. Corre no wasmtime como uma app, é portável entre arquiteturas sem recompilação e fica em sandbox. Só usa CPU e é mais lento do que o nativo. É o formato certo para frotas heterogéneas (documento 08, rodada 5).

## 4. Backends e seleção

```rust
pub trait InferenceBackend: Send + Sync + 'static {
    fn id(&self) -> BackendId;                               // "burn:cuda", "ort:tensorrt", "hailo"
    fn probe(&self) -> Vec<DeviceInfo>;                      // no arranque e em `jk doctor --ml`
    fn supports(&self, m: &ModelManifest) -> Support;        // Yes | No(reason) | Partial(ops)
    fn load(&self, m: &LoadedArtifact, dev: &DeviceInfo, opts: &LoadOpts) -> Result<Box<dyn Session>>;
}

pub trait Session: Send {
    fn infer(&mut self, inputs: &[TensorView], out: &mut [TensorBuf], deadline: Instant) -> Result<Stats>;
    fn warmup(&mut self, n: u32) -> Result<()>;
}
```

- **Cadeia de fallback:** `backend = ["hailo", "burn:vulkan", "ort:cpu"]`. No arranque, o primeiro que `probe` + `supports` aceita é escolhido. Em runtime, N falhas ou deadlines seguidos (por omissão 5) passam ao seguinte, com alarme `ml.<m>.fallback`.
- **Deteção honesta de aceleradores:** um dispositivo Vulkan que é afinal `llvmpipe` (renderização por software) é recusado como GPU. Uma GPU partilhada com o display é marcada `shared`.
- **Cache de kernels:** os backends CubeCL fazem autotune e compilação JIT de kernels. A cache vai para `/var/lib/joker/ml-cache/<device>/<versão>` e é pré-aquecida no `warmup` durante a instalação do modelo, e não na primeira inferência em produção. Sem isto, o primeiro pedido pode demorar segundos.
- **Concorrência:** cada sessão tem `max_inflight` (por omissão 1 em NPU/GPU e N em CPU) e micro-batching opcional (`batch = { max = 8, wait = "5ms" }`).
- **Prioridades:** os pedidos de pipelines com deadline curto passam à frente dos pedidos de tarefas async no mesmo acelerador.
- **Isolamento:** `isolation = "process"` corre a sessão em `joker-ml-<id>`, com tensores em memória partilhada. É a opção para drivers de GPU/NPU capazes de encravar (o supervisor mata e reinicia o processo).

## 5. Pipelines nativos (M5)

Um pipeline liga um stream (ou sinal em bloco) a um modelo e a um sinal ou evento de saída **sem passar pela memória Wasm**:

```
cam0.frames ──▶ crop ──▶ resize ──▶ normalize ──▶ model(detector) ──▶ nms ──▶ vision.detections (evento)
    dmabuf        (CPU NEON ou GPU, conforme o backend do modelo)            └▶ ts_src do frame preservado
```

| Categoria | Operações |
|---|---|
| imagem | `crop`, `resize` (bilinear/area), `letterbox`, `convert` (NV12/YUYV→RGB), `normalize`, `to_tensor(layout)` |
| sinal | `window(n, hop)`, `detrend`, `fft(n, window)`, `bands([…])`, `stats(fields)` (`rms`, `peak`, `crest`, `kurtosis`…), `resample`, `append(signals)` (junta sinais escalares às features) |
| modelo | `model(name)` |
| saída | `nms`, `decode_boxes(anchors)`, `argmax`, `topk`, `threshold`, `softmax`, `to_event(schema)`, `to_signal(field)` (um campo da saída do modelo passa a sinal escalar no `to` do pipeline) |
| controlo | `every(n)` (1 em cada n frames), `when(expr)` (só com uma condição), `correlate(with, window)` (associa cada frame ao flanco com `ts_hw` mais próximo de um sinal de trigger; frame sem flanco ou flanco sem frame geram um evento de erro) |

- Cada passo declara formatos de entrada e de saída, e o `jk check` valida a cadeia (`J0510`).
- **Colocação:** se o modelo corre em GPU, os passos de imagem correm na GPU (kernels CubeCL), e se corre em Hailo, a conversão e o resize correm em CPU NEON. O `jk explain pipeline inspect` mostra onde corre cada passo e a latência estimada.
- **Orçamento de latência:** o pipeline declara `deadline`. Se um frame não termina a tempo, a saída é emitida com a qualidade `bad(deadline)` para que a app decida (no caso da inspeção visual, rejeitar a peça).

## 6. Inferência a partir de apps

```rust
let y = io.forecast.infer([x]).await?;       // Result<Inference, InferError>
match y.quality.code {
    QualityCode::Good      => use_forecast(&y.outputs[0]),
    QualityCode::Uncertain => fallback_plan(),            // OOD
    QualityCode::Bad       => unreachable!(),             // os erros vêm pelo Err
}
```

(Os caminhos completos `QualityCode::…` são necessários: `Good =>` sozinho seria um padrão de ligação que apanha tudo.)

- **Na v1, isto está reservado.** A interface WIT `ml`, a porta `#[model]`, `infer` e `Tensor` existem com `@unstable(feature = ml)` no mundo `joker:runtime` e atrás da feature `unstable-ml` do SDK Rust (sem ela, `J-E0718`). Um componente que as importe é recusado em `mode = "prod"` (`J-E0003`) até à 1.1, e em `dev` liga-se a stubs que devolvem `J-E0601`. As assinaturas previstas estão na ref/04 §2.9 e §4.15, e nos SDKs de tier 2 na ref/05 §20.1; podem mudar até à estabilização.

- As entradas são validadas contra a assinatura (dtype e shape) antes de irem ao backend.
- Tensores até 1 MiB passam pela fronteira Wasm com uma cópia. Acima disso, o `jk check` avisa e sugere um pipeline.
- Um deadline ultrapassado dá `Err(Deadline)`, nunca uma espera indefinida.

## 7. Guarda de entrada e controlador de fallback (M17)

Um modelo treinado em verão não sabe o que fazer com −15 °C. A guarda do `model.toml` compara cada pedido com as estatísticas de treino e marca `Uncertain(OutOfDistribution)` quando elas saem da gama. O que fazer é decisão da app, mas o manifesto oferece o padrão mais comum:

```toml
[apps.hvac_rl.fallback]
controller = "app:hvac_rules"        # outra app, determinista, sempre carregada
when       = "ood_ratio(model:hvac_policy, 15m) > 0.2 || !good(model:hvac_policy)"
```

Enquanto `when` for verdadeiro, o árbitro troca os níveis: o controlador de fallback passa a ocupar o nível do modelo, e o modelo desce para `Shadowed`. Tudo fica registado (documento 08, rodada 6).

## 8. Determinismo e replay (M22)

| Backend | Determinismo |
|---|---|
| Burn Flex / CubeCL CPU | determinista para o mesmo binário e as mesmas flags de CPU (a validar: reduções paralelas) |
| Burn Vulkan/CUDA, TensorRT | **não garantido** (ordem das reduções, autotune) |
| Hailo | determinista para o mesmo HEF e firmware (a validar) |

Por isso **as saídas de modelos com `deterministic != true` são gravadas no traço**, e o `jk replay` usa as gravadas por omissão (`--rerun-models` reexecuta e mostra as diferenças). O replay continua exato para a lógica das apps, que é o que interessa depurar.

## 9. Treino no dispositivo

O Burn treina e infere com o mesmo código, e isso permite algo que ORT/TensorRT não permitem: **adaptar o modelo a cada máquina, no local.**

```toml
[training.pump7_baseline]
arch      = "joker.ae@1"
from      = "models/ae-vibration-base.jkm"         # pesos iniciais (opcional)
data      = { signals = ["pipe:vib7.features"], window = "7d", where = "machine7.running && !any(alarm.**.active)" }
schedule  = "after: 7d of data; then: weekly"
resources = "ml"
priority  = "idle"                                  # SCHED_IDLE; pausa se a CPU rt/io aquecer
budget    = { max_time = "2h", max_memory = "512 MiB" }
checkpoint = "10m"
validate  = { holdout = "20%", metric = "recon_p99", max = 0.08 }
output    = "candidate"                             # nunca produção direta: vai para sombra (M16)
```

- O treino é **preemptível**: faz checkpoint, pausa sob pressão térmica ou de CPU e retoma.
- Os dados vêm do historian e ficam identificados pelo intervalo e pelo hash dos segmentos (linhagem, M10).
- O resultado é um `.jkm` **candidato** que entra em sombra e só depois é promovido.
- A aprendizagem federada (várias máquinas a partilhar deltas de pesos) está fora do núcleo. É possível por cima (uplink de deltas assinados), mas não faz parte do desenho da 1.1 (fica para a v2.x, documento 21).

## 10. Sombra e promoção (M16)

```toml
[models.detector.shadow]
candidate = "models/yolo-s-parts-v8.jkm"
until     = { frames = 50000, duration = "48h" }
promote_if = [
  "agreement(detector, candidate) >= 0.98",
  "latency_p99(candidate) <= 30ms",
  "ood_ratio(candidate, 24h) <= 0.01",
]
on_regress = "demote"                    # após promoção: KPI de regressão → volta atrás
kpi        = "reject_rate(line) within 20% of baseline(7d)"
```

`jk shadow status detector` mostra a concordância, a matriz de confusão entre as duas versões, as latências e os casos divergentes (com frames gravados para rever). A promoção pode ser automática, quando os critérios passam, ou manual (`jk shadow promote`).

---

### 10.1 Expressões de KPI

Os critérios de promoção e de despromoção (`promote_if`, `kpi`, `until`) usam uma gramática **separada** das expressões do documento 02, §10: são avaliados em `bg`, sobre o historian e os traços da sombra, e aceitam janelas longas (até 30 d). Funções: `agreement(a, b)`, `latency_p50/p99(m)`, `ood_ratio(m, janela)`, `false_alarm_rate(m, janela)`, `reject_rate(sinal)`, `baseline(expr, janela)`, `within(x, y, %)`, e os operadores de comparação e lógicos. Não podem ser usadas em permissivos, alarmes nem `calc`.

## 11. Linhagem (M10)

O `lineage.toml` de cada `.jkm` regista: a origem dos dados (hash do dataset, ou intervalos do historian e dispositivo), o commit do código de treino, os hiperparâmetros, as métricas de validação, quem assinou e, para modelos treinados no dispositivo, o `.jkm` pai. O `jk model lineage <m>` mostra a árvore. É a resposta à pergunta "que modelo tomou esta decisão, e com que dados foi treinado?".

## 12. Burn como backend: análise

### 12.1 O que o Burn é hoje

O Burn (Tracel AI, MIT/Apache-2.0) é uma biblioteca de tensores e uma framework de deep learning em Rust, na versão 0.22. Os pontos relevantes para o Joker:

- **Backends:** CubeCL (CUDA, ROCm, Metal, Vulkan, WebGPU, CPU) com fusão de kernels e autodiff; **Flex**, um backend CPU em Rust puro que também corre em `wasm32` e em `no_std`. O backend LibTorch está *deprecated* desde a 0.22.
- **Seleção de dispositivo em runtime:** a API atual escolhe o `Device` em runtime e permite vários backends no mesmo binário. Encaixa diretamente na cadeia de fallback do §4.
- **Treino e inferência com o mesmo código**, incluindo personalização no dispositivo.
- **Importação:** ONNX via burn-onnx (convertido em código Rust; conjunto limitado de operadores), pesos PyTorch e Safetensors via `burn-store`.
- **Backend remoto (beta):** executar tensores num servidor com GPU através de Iroh ou WebSocket.
- **Estado:** em desenvolvimento ativo, com avisos explícitos de breaking changes. A 0.22 mudou o formato dos registos para *burnpack*.

### 12.2 Porque encaixa

| Razão | Porque importa no edge |
|---|---|
| **Rust puro** | um binário estático, cross-compilação simples para aarch64/armv7, sem Python nem libtorch de 1 GB |
| **Portabilidade de backends** | o mesmo modelo corre em CPU, Vulkan (Intel, AMD, Qualcomm e, a validar, a VideoCore do Pi 5), CUDA (Jetson) e Metal (desenvolvimento no Mac) |
| **Flex em `no_std`** | é o mesmo motor de ML para o futuro Joker Micro em MCUs |
| **Flex em Wasm** | modelos pequenos como componentes portáveis (§3.4) |
| **Treino no dispositivo** | adaptação por máquina (rodada 3), que nenhum motor só de inferência dá |
| **Fusão de kernels e JIT** | desempenho competitivo em GPU sem escrever kernels à mão |
| **Mesma linguagem do Joker** | depurar uma inferência não exige atravessar uma fronteira FFI com C++ |

### 12.3 Onde não chega

| Limitação | Consequência | Mitigação |
|---|---|---|
| **Não suporta NPUs** (Hailo, Coral, RKNN, NPUs de SoCs) | num RPi 5 com AI HAT+ ou num RevPi com Hailo, o acelerador principal fica fora do Burn | backend `hailo` (HailoRT) como plugin, com payload HEF |
| **ONNX com operadores limitados** | modelos de terceiros podem não converter | via ORT/tract (§3.3) |
| **ONNX vira código**, não é carregado em runtime | um modelo novo exige compilar | catálogo + pesos (§3.1) para o caso comum, e plugins (§3.2) para o resto |
| **Pré-1.0, com breaking changes** | atualizar o Burn pode partir artefactos | fixar a versão por minor da runtime; os `.jkm` registam a versão do Burn; migração com `jk model migrate` |
| **Em Jetson, o TensorRT é mais rápido em INT8** | o Burn CUDA pode ficar atrás em latência | backend `tensorrt` opcional; medir antes de decidir |
| **Quantização INT8 ainda a amadurecer** (a validar) | modelos grandes em CPU ARM podem ser lentos | ORT com quantização estática como alternativa |
| **Determinismo em GPU não garantido** | afeta o replay | M22 (§8) |
| **Autotune/JIT na primeira execução** | latência alta no arranque | cache persistente e warmup (§4) |

### 12.4 Decisão (ADR 0009)

**Sim ao Burn**, como **backend por omissão e de referência**, e como formato "da casa" para os modelos que o Joker treina ou adapta. **Não como backend exclusivo:** o trait `InferenceBackend` existe desde o primeiro dia, com ORT como segundo backend na Fase 2 e HailoRT como terceiro, porque o hardware alvo mais provável (RPi 5 ou RevPi com Hailo) exige-o.

### 12.5 Matriz hardware × backend

| Hardware | Burn | Outro | Recomendação inicial |
|---|---|---|---|
| RPi 4/5, CM4/CM5 (CPU) | Flex, CubeCL CPU | tract, ORT | **Burn** |
| RPi 5 (GPU VideoCore VII, Vulkan 1.2 via Mesa v3dv) | CubeCL Vulkan (**a validar**: extensões, desempenho) | — | medir; provavelmente CPU ganha em modelos pequenos |
| Hailo-8 / 8L (AI HAT+, M.2) | — | **HailoRT** (HEF) | Hailo para visão; Burn CPU para séries temporais |
| Jetson Orin | CubeCL CUDA | TensorRT, ORT-TRT | Burn por omissão; TensorRT se o benchmark o justificar |
| x86 + NVIDIA | CubeCL CUDA | TensorRT | Burn |
| x86 Intel iGPU | CubeCL Vulkan | ORT-OpenVINO | medir |
| Coral Edge TPU | — | libedgetpu (plugin X) | só se houver procura |
| Rockchip RK3588 NPU | — | RKNN (plugin X) | só se houver procura |
| MCU (Joker Micro) | Flex `no_std` | — | Burn |
| Mac (desenvolvimento) | CubeCL Metal | — | Burn |

### 12.6 O que validar na 1.1 (portas de saída)

1. Latência e memória de `joker.tcn@2`, `joker.ae@1` e `joker.cnn1d@1` em Burn Flex e CubeCL CPU num CM4 e num CM5, face ao tract e ao ORT.
2. CubeCL Vulkan na VideoCore VII: funciona? E ganha à CPU?
3. Determinismo do Flex entre execuções e entre CM4 e CM5.
4. Treino do `joker.ae@1` com 7 dias de features (≈ 600 k janelas) num CM5 em menos de 2 h, em `SCHED_IDLE`, sem afetar o jitter do grupo `rt`.
5. burn-onnx: percentagem de conversão com sucesso num conjunto de 20 modelos típicos de edge (YOLO pequenos, MobileNet, EfficientNet-Lite, TCN, LSTM).
6. YOLO-s em Hailo-8L via HailoRT: latência de ponta a ponta do pipeline, com zero-copy desde a câmara.

Se o ponto 1 falhar por mais de 2× face ao ORT, o backend por omissão em CPU passa a ORT e o Burn fica para GPU e treino. A decisão fica registada numa ADR.

## 13. LLMs e VLMs locais

Modelos de linguagem locais (via `mistral.rs`, `candle` ou `llama.cpp` num processo tier X `joker-llm`) são suportados como **servidores de modelo**, e não como backends do caminho de controlo. Um assistente que use um LLM é uma app com `writer.kind = "proposal"` (M18): pode ler, explicar e propor, mas nunca escreve sem aprovação humana (documento 08, rodada 6).
