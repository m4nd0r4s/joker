# ref/03 — Profiles, boards, simulation, scenarios, conformance and packages

Complete reference of the **catalog** TOML files (device profiles, boards, class packages) and of the **test** TOML files (simulation models, scenarios, conformance cases of the core and of the classes), and of how catalog artifacts are published to the Hub. It applies `ref/00` without repeating it. The semantics (arbiter, envelope, quality, expressions) are those of document 16; this reference holds the representation and the validation.

## 2. The reference

### 2.1 Rules common to all files

#### 2.1.1 Header

| Key (root) | Type | Required | Default | Validation |
|---|---|---|---|---|
| `schema` | integer | yes | — | must be the **first key/value pair** of the file; before it only comments and empty lines (`J0800`); value `1` in v1 (`J0801`). It is the rule of ref/00 §1 (D11) |
| `joker` | string `"M.m"` | no | `"1.0"` | minimum version of the runtime that reads the file; an older runtime rejects it with `J0802`, and not with `J0140` |

- The **type** of the file (profile, board, model, scenario, suite, fixture, package) comes from the **name suffix** (`.profile.toml`, `.board.toml`, …; ADR 0026) and, in an OCI artifact, from the media type (§2.8). The content must match the suffix, and whoever refers to the file must ask for that type: the two checks and `J0803` are in §2.1.6.
- Each type with a publishable name, and the driver fixture, has a required identification table: `[profile]`, `[board]`, `[package]`, `[scenario]`, `[suite]`, `[fixture]`. The simulation model has no publishable name, and the `[model]` table is optional; it is recognized by the keys of §2.1.6.
- **Strict** (ref/00 §1): an unknown key is `J0140`; keys starting with `x_` are ignored at any level; keys starting with `_` are reserved (`J0141`, as in the manifest).
- Encoding: TOML 1.0, UTF-8, no BOM. Maximum size of a file: 4 MiB.

#### 2.1.2 Names

| Thing | Grammar | Example | Error |
|---|---|---|---|
| profile name | `seg "/" seg`, with `seg := [a-z0-9]+ ("-" [a-z0-9]+)*`, ≤ 64 characters in total | `eastron/sdm630`, `acme/pcs-125`, `local/xy-md02` | `J0805` |
| profile reference | `<name>@<major>` | `acme/pcs-125@3` | `J0805` |
| board name | `seg` (same grammar), ≤ 48 characters | `rpi5`, `revpi-connect-5`, `rp2350-pico2` | `J0805` |
| class package | `ident ("/" ident)*` (document 17, §3.2), `ident := [a-z][a-z0-9_]*` | `std`, `acme/water` | `J0805` |
| relative signal path (profile, model) | the one of 02 §9, without the device segment: at most 7 segments | `l1.v`, `status.fault` | `J0805` |
| enum name | `[A-Z][A-Za-z0-9]*`, ≤ 32 | `PcsState` | `J0805` |
| variant, bit, action, argument, parameter, coherent group | `[a-z][a-z0-9_]*`, ≤ 32 | `p_control`, `reset_fault` | `J0805` |
| case and suite id | `[a-z0-9_]+ ("." [a-z0-9_]+)*`, ≤ 96 | `envelope.rate.clamp_then_safe` | `J0805` |

**Reserved namespaces:** `joker/` (profiles generated by or embedded in the runtime: `joker/sunspec@1`, Joker Link profiles); `local/` (profiles and packages of the project, which are **never** published: `J0848`); `std` (standard class package, published only by the project). A name inside a reserved namespace outside its place is `J0805`.

**The file and the name agree:** `profiles/eastron/sdm630@1.profile.toml` has `name = "eastron/sdm630"` and `version = "1.x.y"`; `boards/rpi5.board.toml` has `name = "rpi5"`; `classes/acme/water/water.package.toml` has `name = "acme/water"`. A mismatch is `J0804`.

#### 2.1.3 Literals

All literals follow ref/00 §3 and §4. A malformed literal is `J0806`.

| Literal | Grammar | Examples | Where |
|---|---|---|---|
| duration | ref/00 §3.1 | `"500ms"`, `"1.5s"`, `"10m"` | duration keys |
| quantity | ref/00 §3.2; unit of the catalog (16 §5, `J0109`) | `"3.3 V"`, `"-20 kW/s"`, `"5 %"` | physical values |
| bare number | TOML integer or decimal | `1.65`, `0x48` | value **in the declared unit** of the signal |
| instant (timeline) | `duration ("+" duration)*`, optional spaces around `+`; in driver suites, one of the terms may be `timeout` (§5, ref/06 §6.3) | `"3m"`, `"2m+1.2s"`, `"100ms + timeout + 50ms"` | `at`, `before`, interval bounds — **only** in scenarios and cases (ref/00 §3.1) |
| interval | `instant ".." instant`, closed at both bounds, with `start ≤ end` | `"2s .. 5s"` | `during`, `within` |
| tolerance | `duration ("±" \| "+-") duration` | `"500ms ± 20ms"` | `toggles_every` |
| quality | `code` \| `code "(" reason ")"`, names of ref/00 §4.3 in `snake_case` | `"good"`, `"bad(comm_failure)"`, `"uncertain(stale)"` | `quality` |
| write result | `result` \| `"rejected(" reason ")"` \| `"overridden(" level ")"`, names of ref/00 §4.4 | `"clamped_rate"`, `"rejected(interlock)"`, `"overridden(manual:4)"` | `outcome` |
| alarm state | ref/00 §6 `alarm_state` | `"active_unacked"`, `"unknown"` | `state` |
| arbiter level | ref/00 §5, or `"none"` | `"optimizer:13"` | `level` |
| enum value | `"variant"` or `"Enum.variant"` | `"fault"`, `"StatusMode.off"` | values of enum signals |

**Accepted display forms** (ref/00 §2; D10). The CLI shows `Bad(CommFailure)`, `Clamped(Rate)`, `Rejected(Interlock)`, `Unknown`, and it is natural to copy them into a file. Therefore, in `quality`, `outcome` and `state`, the display form is accepted as an exact synonym of the canonical one, with this translation: `PascalCase` → `snake_case`, `Clamped(Range|Rate)` → `clamped_range|clamped_rate`, `Overridden(level)` → `overridden(level)`. It is a total and unambiguous translation; `jk fmt` rewrites to the canonical form. Any other spelling is `J0806`.

**Units in values.** A value with a unit is converted to the unit of the signal (different dimension: `J0107`; different quantity: `J0108`). A bare number is in the unit of the signal. `%` is not converted to `1` nor the other way around (02 §3).

#### 2.1.4 Selectors

Wherever a signal path is accepted in a scenario or in a case, a selector of 02 §9 is accepted (`*` in one segment, `**` in several). A selector expands in `jk check` to the ordered list of signals that match it; zero matches is `J0841`. The semantics of an expectation with a selector is "**all** the matched signals comply", unless stated otherwise.

|---|---|

| signals per simulation model | 1,024 |
| variants per enum | 256 |
| named bits per signal | 64 |

#### 2.1.6 The type is in the name

The general rule for file names is in ref/00 §2 (ADR 0026). In this reference:

| Suffix | Type | Recognized by the content through | Who refers to it |
|---|---|---|---|
| `.profile.toml` | device profile (§2.2) | `[profile]` | `profile = "<name>@<major>"` (resolution by name, §3), `[model] profile`, `[fixture] profile`, `jk profile …` |
| `.board.toml` | board (§2.3) | `[board]` | `[target] board = "<board>"` (resolution by name), `jk board …` |
| `.sim.toml` | simulation model (§2.4) | at least one of `[model]`, `[signals]`, `[plant]`, and no identification table of another type | `model = "<path>"`, class simulator (§2.4.11) |
| `.scenario.toml` | scenario (§2.5) | `[scenario]` | `jk test [<path>…]`, directory `sim/scenarios/` |
| `.conformance.toml` | conformance suite (§2.6) | `[suite]` | `jk class verify`, `jk driver test`, core runner |
| `.fixture.toml` | driver fixture (ref/06 §6.2) | `[fixture]` | `jk driver test --fixture <path>` |
| `.driver.toml` | driver descriptor in TOML (ref/06 §2.3) | `name`, `tier` and `protocols` at the root | `jk driver meta` |
| `.package.toml` | class package (§2.7) | `[package]` | `jkc`, `jk class publish` (one per package directory) |

**Content ↔ suffix check (`J0803`).** Before the validation of the keys (§3, "Validation"), `jk check` reads the top-level tables of each file and confirms that they match the suffix. It is `J0803`:

- a file without the identification table of its suffix (a `.board.toml` without `[board]`), or a `.sim.toml` without any of the keys that characterize it;
- a file with the identification table of **another** type (a `.sim.toml` with `[profile]`), or of two types;
- a file referred to by someone asking for another type (`model = "profiles/local/xy-md02@1.profile.toml"`; `jk test boards/rpi5.board.toml`);
- a TOML file in one of these directories (`profiles/`, `boards/`, `sim/`, `conformance/`, `classes/`) without any of the suffixes of the table. `jk migrate` renames it (document 07, §2).

The message states the type expected from the suffix and the type the content shows ("`sim/esp.sim.toml` has `[profile]`: it is a profile; a profile is named `<model>@<major>.profile.toml` and lives in `profiles/`"). `J0803` comes before `J0140`: a profile with the name of a simulation would otherwise give a list of unknown keys.

**Resolution by name.** Profiles and boards are referred to by name, without suffix; the resolution adds it (§3): `local/bench-esp32@1` → `profiles/local/bench-esp32@1.profile.toml`; `rpi-zero-w` → `boards/rpi-zero-w.board.toml`. File paths (`model`, `manifest`, `--fixture`) are written in full, with the suffix.

**Editors.** `jk init` and `jk new` write at the project root a `.taplo.toml` that associates each suffix (and `joker*.toml`) with the JSON schema of its type (generated from the Rust types, like the one of the manifest, and published with each version of `jk`); `jk migrate` adds it to an old project. The file is versioned, and `jk` does not rewrite it if it already exists.

### 2.2 Device profiles

A profile describes a **model** of equipment (15 §1). The driver delivers raw values; the acquisition stage of the core applies, from the profile, raw type, byte order, scale, offset, unit, limits and freeze detection (01 §3.3). The `plan` of the driver (05 §2) validates what is protocol-specific; `jk check` validates everything else without I/O.

#### 2.2.1 Structure

```toml
schema = 1

[profile]            # identification, protocol, quirks
[defaults]           # defaults of the points
[signals]            # points: one per signal
[enums]              # named enums
[coherent]           # groups read in the same request
[config]             # schema of the device's `config` in the manifest
[fallback]           # M1: fallback of the equipment itself
[actions]            # actions (M19)
[connect]            # steps at connection startup
[relinquish]         # steps of `safe = "relinquish"`
[events]             # device events
[implements]         # classes fulfilled (implicit instances)
[discovery]          # discovery (SunSpec)
```

All sections are optional except `[profile]` and `[signals]` (the latter may be empty only in a discovery profile).

**What the 1.0 runtime reads** (ADR 0064, by ADR 0028). A key, section or form of this section that the runtime does not implement yet is refused with `J0807`, and the profile is not loaded, instead of being read without it: the sections `[coherent]`, `[config]`, `[connect]`, `[relinquish]`, `[events]` and `[discovery]`; `[profile]` `firmware` and `identity`; the point keys `quantity`, `scale_factor`, `bits`, `encoding`, `invalid`, `max_age`, `limits` and `stuck_detect`, the two-point `scale`, an `offset` quantity, `signal_type = "f32"` and `kind` other than `scalar`; and the register forms of `[fallback]` and its `behavior`. An output whose value is converted to raw (`scale`, `offset`, `invert`, `enum`, or a float on an integer raw type) is converted by the output stage of `ref/06` §2.7 (ADR 0075). A `bool` output in a register bit is written by read-modify-write (§2.2.5, ADR 0076). `label`, `description`, `readback`, `safe_hint`, `range_hint` and `monotonic` are accepted: they change no value the runtime produces. `[defaults]` `poll` and `timeout` are the device defaults. Each refused surface is accepted, unchanged, in the minor that implements it.

#### 2.2.2 `[profile]`

| Key | Type | Req. | Default | Validation and meaning |
|---|---|---|---|---|
| `name` | string | yes | — | §2.1.2; equal to the path (`J0804`) |
| `version` | SemVer | yes | — | major equal to the `@major` of the file (`J0804`) |
| `driver` | string | yes | — | driver family (table below); the `driver` of the device must belong to the family (`J0808`) |
| `vendor` | string ≤ 64 B | no | — | manufacturer, free text |
| `model` | string ≤ 64 B | no | — | commercial designation |
| `description` | string ≤ 1 KiB | no | — | |
| `docs` | URL | no | — | datasheet |
| `license` | SPDX expression | no (yes to publish, `J0848`) | — | license of the profile file |
| `authors` | list of strings | no | `[]` | |
| `firmware` | SemVer constraint string (`">=4.10, <5"`) or list of exact strings | no | no constraint | compared with the firmware read at `connect`; out of range: `J0826` (warning in `dev`, error in `prod`) |
| `identity` | table `{ firmware = "<point>" }` | no | `{}` | where the identity comes from in a piece of equipment **without discovery** (a Modbus device without SunSpec): `firmware` is the name of a point of `[signals]` of this profile, with `direction = "input"` or `"param"` (a nonexistent point, or an output, is `J0825`). The value read is turned into text (a `string` as it is; an integer in decimal; with `enum`, the label) and is the `firmware` of the device: `jk lock --node` writes it to `[discovered.<d>] firmware` (ref/02 §2.1.11), the `firmware` constraint above (`J0826`) compares it, and the drift `J0401 kind=firmware` (ref/02 §3.1.5) works without `discover = true`. | `quirks` | table | no | `{}` | protocol adjustments, per family (§2.2.6); unknown key for the family: `J0818` |

#### 2.2.3 `[defaults]`

Any point key of the table of §2.2.4 marked "yes" in the *default* column may have a default here. A point that declares the key wins. Key not admitted in `[defaults]`: `J0140`.

#### 2.2.4 `[signals]`: keys of a point

The key of each entry is the relative path of the signal (in quotes when it has dots). The full path in the site is `<device>.<path>`. The first segment `actions` is reserved (`J0805`), because `actions.<name>` is a reference to an action in the mappings (§2.2.13).

| Key | Type | Req. | Default | In `[defaults]` | Validation and meaning |
|---|---|---|---|---|---|
| address | see §2.2.5 | yes | — | partial | depends on the family |
| `type` | raw type (§2.2.7) | yes | — | yes | `J0809` if invalid for the address |
| `signal_type` | `bool` `i64` `u64` `f64` `f32` | no | derived (§2.2.7) | yes | only to force `f32` or integer; `J0815` if incompatible |
| `direction` | `input` \| `output` \| `param` | no | `input` | yes | `output` requires a write address (`J0810`); outputs need an envelope in the manifest (`J0201`) |
| `unit` | unit | no (yes for physical quantities) | `1` | yes | catalog 16 §5 (`J0109`); forbidden in `bool`, `enum`, `bits`, `string`, `bytes` (`J0815`) |
| `quantity` | quantity of 16 §5 | no | the one of the unit | no | `J0108` if incompatible with the unit |
| `scale` | number ≠ 0, or `{ from = [a, b], to = [c, d] }` | no | `1` | yes | value = raw × `scale` + `offset`; the two-point form: `from` in raw units, `to` in quantities; `J0815` in `bool`, `enum`, `bits` |
| `offset` | number (in the unit of the signal) or quantity | no | `0` | yes | not combined with the two-point form (`J0815`) |
| `scale_factor` | path of another point | no | — | no | scale = 10^(integer value of the indicated point) (SunSpec `*_SF`); the point is **automatically coherent** with this one (§2.2.9); multiplies with `scale` |
| `enum` | name in `[enums]` | no | — | no | type of the signal `enum<Name>`; `J0814` if it does not exist |
| `bits` | table `index → name` | no | — | no | only in `bits16`, `bits32`, `bits64`; index 0 = least significant bit; each name creates the derived `bool` signal `<path>.<name>` with the same `acq_id` (§2.2.8) |
| `bit` | integer | no | — | no | extracts a single bit of a register as `bool` |
| `invert` | bool | no | `false` | no | only in `bool` (inverted logic) |
| `len` | integer | cond. | — | no | required in `string` and `bytes` (in registers or bytes, depending on the family); ≤ 64 B after decoding |
| `encoding` | `ascii` \| `utf8` | no | `ascii` | yes | `string` |
| `invalid` | list of raw values | no | `[]` | yes | a raw value in this list gives `bad(nan)` ("not implemented", `0x8000` in SunSpec) |
| `poll` | duration or `"on_demand"` | no | the `poll` of the device | no | `"on_demand"` only with `direction = "param"` (`J0817`); `param` without `poll` is `"on_demand"` |
| `max_age` | duration | no | 3 × `poll` (01 §3.3) | yes | `J0816` if ≤ `poll` |
| `limits` | `[min, max]` (quantities or numbers) | no | — | no | **physical** limits: outside them, `bad(out_of_range)` (02 §4); `min < max` (`J0816`) |
| `stuck_detect` | duration | no | — | yes | `uncertain(frozen)` when the value stays bit-for-bit equal for that time (02 §4) |
| `deadband` | quantity | no | — | no | **acquisition** deadband (inputs only; on outputs the deadband belongs to the envelope, in the manifest) |
| `monotonic` | bool | no | `false` | no | counter (energy, hours): the historian aggregates by the last value and not by the mean; a decrease does not change the quality and is counted in the metric `joker_counter_resets_total{signal}` |
| `readback` | path of another point | no | — | no | only in `output`: suggests the `verify.readback` of the manifest (`jk check` shows the suggestion) |
| `safe_hint` | value | no | — | no | only in `output`: suggestion for `safe`, shown next to `J0201`; never applied |
| `range_hint` | `[min, max]` | no | — | no | only in `output`: nominal range of the equipment, shown in `jk check` |
| `label` | string ≤ 64 B | no | — | no | for HMI and `jk read` |
| `description` | string ≤ 1 KiB | no | — | no | |
| `kind` | `scalar` \| `block` \| `stream` | no | `scalar` | no | `block` and `stream` reserved for 1.1 (`J0807`) |

The adjustments of the manifest (`[devices.<d>.signals]`, `[signals."<path>"]`) override, on a profile point, only `alias`, `max_age`, `limits`, `stuck_detect`, `deadband`, `debounce`, `scale`, `offset` (applied after those of the profile), `unit` (of the same dimension), `poll` and `record` (ref/01 §5.8.1, with the same grammar: the two-point `scale` is `{ from, to }` in both places); the remaining ones belong to the profile. None of these reaches the driver: they belong to the acquisition stage (ref/06 §2.4).

#### 2.2.5 Addressing per family

**Generic keys and address keys.** The keys of a point split into two families, validated by whoever understands them:

| Keys | Who defines them | Who validates them | Errors |
|---|---|---|---|
| generic (§2.2.4: `type`, `direction`, `unit`, `scale`, `limits`, `enum`, `poll`, …) | this reference, the same for all drivers | the core, in `jk check`, without the driver | `J0809`, `J0814`–`J0817` |
| address (this section) | the `address` schema of the driver descriptor (ref/06 §2.3); for the catalog drivers, the tables below | first the core, by the schema (type, range, values: `J0853`); then the `plan` of the driver, by protocol coherence | `J0809`–`J0813` |
| `quirks` (§2.2.6) | the `quirks` schema of the descriptor | same | `J0818` |
| `native` of the actions (§2.2.12) | the `native` schema of the descriptor | same | `J0821` |

A key that is neither generic nor from the driver's address schema is `J0140`. `plan` only returns codes of this reference (§2.9) or of ref/06 (`J085x`); a code from another range, or none, is `J0855` (ref/06 §2.6). Thus, a tier X driver whose executable does not run on the laptop still has its keys validated in `jk check`.

**Modbus** (complete in 1.0):

| Key | Type | Req. | Default | Validation |
|---|---|---|---|---|
| `at` | integer 0–65535 | yes | — | **protocol** address, **base 0** (track 4, §4.1: "30001" is input register 0); `at + registers − 1 ≤ 65535` (`J0810`) |
| `fc` | 1, 2, 3, 4, 5, 6, 15, 16 | yes (in `[defaults]` or in the point) | — | inputs and `param`: 1 (coils), 2 (discrete inputs), 3 (holding), 4 (input registers); outputs: 5, 6, 15, 16 (`J0810`) |
| `word_order` | `big` \| `little` | no | `big` | types of more than one register |
| `byte_order` | `big` \| `little` | no | `big` | within each register |
| `bit` | 0–15 | no | — | only with `type = "bool"`: with FC 3/4, extracts a bit of a register; on an output with FC 6/16, writes that bit by read-modify-write (ADR 0076) |

- FC 1/2 and FC 5/15 only accept `type = "bool"` (`J0809`). FC 6 only accepts single-register types (`J0809`); types of 2 or 4 registers on an output require FC 16.
- **Writing an output** (ADR 0076). FC 5 and 15 write one coil; FC 6 writes one register; FC 16 writes the registers of the type, in the order the output stage laid them out (`word_order`, `byte_order`). A `bool` output with `bit` (FC 6 or 16) is a read-modify-write: the driver reads the register with FC 3, sets or clears the bit and writes the register back; if the read fails, nothing is written and the write fails with it. The two requests are not atomic against another Modbus client writing the same register; within the node they are not interleaved with other requests of the device. A write is confirmed by its echo (FC 5/6: the request; FC 15/16: address and count); any other answer is `comm-failure`.
- **Reading an output.** An output is not read in the cycle: its slot holds the applied value. The readback is read through an input point at the same address (`p_set_rb` with FC 3), which is the only overlap case allowed besides points that read exactly the same registers (bits of a register, different `bit`).
- Any other register overlap between points of the same space (read FC) is `J0811`.

**I²C and SPI:**

| Key | Type | Req. | Validation |
|---|---|---|---|
| `reg` | integer 0–65535 | one of `reg` or `channel` | chip register |
| `len` | 1–64 bytes | with `reg` | |

| `channel` | integer 0–255 | one of `reg` or `channel` | channel of a *chip handler* of the driver (`[profile] quirks.chip`), for chips with read sequences (ADCs with multiplexer: ADS1115) |

#### 2.2.7 Raw types and signal type

| `type` | Modbus registers | Default signal type |
|---|---|---|
| `bool` | coil/discrete, or 1 bit (`bit`) | `bool` |
| `u16`, `i16` | 1 | `u64`/`i64`; `f64` if there is `scale`, `offset`, `scale_factor` or `unit` ≠ `1` |
| `u32`, `i32` | 2 | same |
| `u64`, `i64` | 4 | same |
| `f32` | 2 | `f64` (ref/00 §4.1); `signal_type = "f32"` keeps `f32` |
| `f64` | 4 | `f64` |
| `bits16`, `bits32`, `bits64` | 1, 2, 4 | `bits<N>` |
| `string` | `len` registers (2 characters per register) | `string` |
| `bytes` | `len` registers | `bytes` |

An `enum` uses a raw integer type and gives `enum<Name>`. A NaN or infinity in an `f32`/`f64` gives `bad(nan)`. An integer raw value that does not fit in the signal type (a `u64` > 2⁶³ with `signal_type = "i64"`) gives `bad(out_of_range)`.

#### 2.2.8 `[enums]` and bits

```toml
[enums]
PcsMode  = { off = 0, standby = 1, p_control = 2 }
```

- Each enum is a table `variant → integer`. Values unique and within the range of the raw type of the points that use it (`J0814`).
- A raw value without a variant gives `bad(out_of_range)`.
- **Scope:** the enum belongs to the profile. Its full name is `<profile>@<major>::<Name>` (`acme/pcs-125@3::PcsState`), and that is what the registry stores. In manifest expressions (`pcs.state == PcsState.fault`), the literal is resolved by the type of the other operand; a literal that has no typed operand (`PcsState.fault` alone) and whose name exists in more than one profile of the site is `J0303` with the list of candidates. It is the ambiguity rule of this reference, the same as that of profile resolution (§3, "Resolution"): an ambiguity is always an error with the candidates, and never a silent choice.
- **Named bits:** `bits = { 0 = "running", 3 = "fault" }` creates `status.running` and `status.fault` as derived `bool` signals, read with the parent signal (same `acq_id`). A bit outside `0..N−1` or two equal names are `J0814`; a name that collides with another signal of the profile is `J0811`.

#### 2.2.9 `[coherent]`

```toml
[coherent]
power = ["p_total", "q_total"]
```

Table `group name → list of paths`. The signals of a group are read **in the same request** (02 §6.2, 05 §4): same address family, same FC, within `max_regs`, with no `forbidden` in between. The gap between them may exceed `max_gap`. A group that does not fit in one request is `J0813`, detected by `plan` in `jk check`. A signal may be in more than one group; groups that share signals are merged. The point/`scale_factor` pairs are implicit groups.

#### 2.2.10 `[config]`: schema of the device configuration

The key `config = { … }` of `[devices.<d>]` in the manifest (for example, on an I²C ADC, `config = { pga = "4.096 V", rate = "128 SPS" }`) is validated against this section.

| Key of `[config.<key>]` | Type | Req. | Meaning |
|---|---|---|---|
| `type` | `choice` \| `bool` \| `integer` \| `number` \| `quantity` \| `string` | yes | `choice`: one of the strings of `values` (it is not a quantity literal: `"128 SPS"` is a label) |
| `values` | list of strings | with `choice` | accepted values |
| `unit` | unit | with `quantity` | |
| `range` | `[min, max]` | no | `integer`, `number`, `quantity` |
| `default` | value | no | without `default`, the key is required in the manifest |
| `apply` | list of steps (§2.2.12) | no | write at `connect`, with `"$value"` as the chosen value; without `apply`, the value goes to the `plan` of the driver (*chip handlers*) |
| `description` | string | no | |

Undeclared `config` key, value outside `values` or `range`, or required key missing: `J0819`. In the manifest, `config` is a table in the drivers that accept it (ref/01 appendix A); the values without `apply` reach the driver in `device-spec.profile-config`, and those with `apply` are written by the core with `write-addr` (ref/06 §2.4.1, §2.10). It is different from the `config` of the driver descriptor, which is the schema of the direct keys of `[devices.<d>]` (`address`, `unit_id`…).

#### 2.2.11 `[fallback]` (M1)

The fallback of the equipment itself, checked against the `safe` and the `safer` of the manifest (01 §8; the coherence error is still `J0205`).

| Key | Type | Req. | Meaning |
|---|---|---|---|
| `timeout_register` | point address (§2.2.5) with `type`, `unit` (duration) and `scale` | one of `timeout_register` or `timeout` | register of the lost-communication time |
| `timeout` | duration | same | fallback with a fixed time (not configurable) |
| `value_register` | point address with `type`, `unit`, `scale` | one of `value_register`, `value` or `values` | register of the value applied in fallback |
| `value` | value | same | fixed value |
| `values` | table `output → point address or value` | same | one value per output (several setpoints with a single timer); replaces `applies_to` |
| `applies_to` | list of outputs of the profile | no | outputs covered, with `value_register`, `value` or `behavior = "hold"`. **Without `applies_to`** (and without `values`), `[fallback]` covers **all** outputs of the profile (`direction = "output"`); the lock records them in full in `outputs` |
| `behavior` | `value` \| `hold` | no (default `value`) | `hold`: the equipment keeps the last value; it is only coherent with `safer = "equal"` and a `safe` equal to the last applied one, which is almost never true: `J0205` in `prod` |
| `enable_register` | point address + `enable_value` | no | equipment in which the fallback must be enabled |
| `configurable` | bool | no (default `true` if there are registers) | `false`: the driver only reads and checks, never writes (even with `fallback.configure = true` in the manifest) |

In the register entries, `point = "<model>.<point>"` may be used instead of the address, in a discovery profile (§2.2.15). Reference to an output that does not exist or is not `output`, or a register without a duration unit: `J0820`.

**In the lock.** `jk lock --node` pins what it read in `[fallback.<device>]` (ref/02 §2.1.12), field by field: `applies_to` or the keys of `values` → `outputs`; `timeout_register` → `register`; `value_register` → `value_register`; the value read or `timeout` → `timeout`; the value read or `value` → `value`; `values` → `values`; `behavior` → `behavior`. `configured` is the `fallback.configure` of the manifest (ref/01 §5.8), always `false` with `configurable = false`. The registers are read and written by the core with `read-addr`/`write-addr` (ref/06 §2.1, steps 4–5).

#### 2.2.12 `[actions]` and the step language

```toml
[actions.reset_fault]
steps = [{ write = { at = 40300, fc = 6, value = 1 } }, { wait = "500ms" }, { write = { at = 40300, fc = 6, value = 0 } }]
```

| Key of `[actions.<name>]` | Type | Req. | Default | Meaning |
|---|---|---|---|---|
| `steps` | list of steps | one of `steps` or `native` | — | executed in order in the serialized queue of the device (02 §8) |
| `native` | opaque table | same | — | operation of the driver itself (OPC UA method, CANopen SDO), validated by `plan` |
| `args` | table `name → type` (`"f64 %"`, `"bool"`, `"u64"`, `"i64"`, `"Enum"`) | no | `{}` | typed arguments, all required; `"$name"` in a step is the value of the argument, converted as ADR 0066 §5 says (a quantity to the declared unit, an enum variant to its value) |
| `result` | table `name → type` | no | `{}` | fields of the result, filled by `read` steps with `into` |
| `timeout` | duration | no | sum of the `wait`s + 1 s per step | the action's default; the manifest wins (17 §4.2) |
| `long` | bool | no | `false` | returns an `ActionHandle` with progress (M19) |
| `description` | string | no | — | |

**Steps** (each step is a table with exactly one of these keys):

| Step | Form | Semantics |
|---|---|---|
| `write` | `{ <address>, type?, value \| "$arg" }` | writes a raw value (without scale) or, with `signal = "<output>"`, a value in the unit of the signal (with scale); **does not go through the envelope** (it is an action, 17 §2.1), but goes through the permissive and the role of the action |
| `read` | `{ <address>, type, into = "<field>" }` | reads and stores in the result |
| `wait` | duration | waits |
| `until` | `{ <address>, type, equals, timeout }` | reads until the value matches or the time runs out (then `Err(timeout)`) |
| `fail_if` | `{ <address>, type, equals, message }` | ends with `Err(message)` if the value matches |

**Quality of a step's read** (ADR 0060, 16 §3.2): a `Bad` read in `read`, `until` or `fail_if` ends the action with `Err(device)` naming the quality reason, and its raw value is never compared or stored; an `Uncertain` read ends a `fail_if` the same way, is not a match for `until` (it keeps polling), and enters the result of `read` with its flag. A step the interpreter cannot resolve (a non-scalar type, an unresolved `$arg`) is `Err(unsupported)`, never a communication failure.

Address in a `forbidden`, unknown step, `wait` above the `timeout` or undeclared `$arg`: `J0821`. Missing arguments or arguments with the wrong type in an invocation: `J0822` (in `jk check` for actions called by known expressions; at runtime, `Err(invalid_args)`).

#### 2.2.13 `[connect]`, `[relinquish]` and `[events]`

| Section | Keys | Meaning |
|---|---|---|
| `[connect]` | `steps` (list of steps) | executed after each connection, before the first poll (remote mode, write unlock); failure → link `Down` |
| `[relinquish.<output>]` | `steps`, or `native = true` | what `safe = "relinquish"` does on that output (03 §6.1); `native = true` only in drivers with a *priority array* (BACnet, 1.2). An output with `safe = "relinquish"` without an entry here and without native support: `J0207` |
| `[events.<name>]` | `on_rise` or `on_change` (path), `fields` (table `field → path`) | device event `<d>.<name>` without needing a class; the same adapters as 17 §5.2 |

#### 2.2.14 `[implements]`

A profile (or a simulation model, §2.4.9) declares the classes that the equipment fulfills. Each device with the profile is an implicit instance of those classes, with the name of the device (14 §5.1).

```toml
[implements."std/pump@1"]
capabilities = ["variable_speed", "hour_counter"]
map = { run_cmd = "cmd.run", running = "status.running", fault = "status.fault", speed_set = { signal = "speed_ref", scale = 0.01 }, reset = "actions.reset_fault" }
```

| Key | Type | Req. | Default | Validation |
|---|---|---|---|---|
| table key | class reference `<package>/<name>@<major>` (`std/` may be omitted) | — | — | unknown class or nonexistent major: `J0823` |
| `capabilities` | list | no | `[]` | capabilities that the equipment has; a required member of a declared capability without mapping is `J0602` |
| `map` | table `member → target` | yes | — | required member without target: `J0601`; member of a capability **not** declared: `J0824` |

**Targets** (17 §5.2):

| Form | Members | Example |
|---|---|---|
| relative path of a signal of the profile | `in`, `out`, `param` (compatible direction: `out` → `output`, `in` → `input`/`param`, `param` → `param`/`input`) | `"status.running"` |
| `"actions.<name>"` | `action` | `"actions.reset_fault"` |
| `"const:<literal>"` | only `in` and `param` (`J0603` on an `out`) | `"const:true"`, `"const:12 m3/h"` |
| `{ signal, scale?, offset?, invert? }` | `in`, `out`, `param` | `{ signal = "speed_ref", scale = 0.01 }`: member = signal × `scale` + `offset`; on an `out`, the inverse is applied to the proposal |
| `{ signal, enum_map }` | enums | `{ signal = "op_mode", enum_map = { off = 0, standby = 3 } }` |
| `{ edge = { rise, fall } }` | `out bool` | actions triggered on the edges of the applied value (17 §5.2) |
| `{ on_rise \| on_change, fields }` | `event` | `{ on_rise = "status.fault", fields = { code = "fault_code" } }` |

Incompatible direction, adapter on a member of the wrong type, `scale` with a dimension (it must be a number) or nonexistent event field: `J0824`. Nonexistent signal: `J0101`. Incompatible unit between the signal and the member: `J0107` (conversion between units of the same dimension is automatic).

Several implicit instances per device (a 4-channel ADC as 4 × `analog_in@1`) are reserved for 1.x (key `instances`, `J0807`); in 1.0 they are made as composite instances in the manifest.

**Composite classes** (document 17, §8). A piece of equipment that already is the whole composition (a Modbus controller that is the entire heat pump) fulfills the composite class in a single `[implements]`: each class member has a subtable `members.<member>`, with the `map` of that member over the points **of the same profile**.

```toml
# profiles/acme/hp-ctrl@1.profile.toml (excerpt; the members of drive@1 and meter.ac3@1 are abbreviated)
[implements."local/heat_pump@1"]
map = { mode = { signal = "hp.mode", enum_map = { off = 0, heat = 1, boost = 2 } }, flow_sp = "hp.flow_sp" }

[implements."local/heat_pump@1".members.compressor]
map = { discharge_temp = "comp.t_discharge" }

[implements."local/heat_pump@1".members.compressor.members.drive]
map = { run_cmd = "comp.run", speed_set = { signal = "comp.speed_ref", scale = 0.1 }, speed = "comp.speed" }

[implements."local/heat_pump@1".members.t_supply]
map = { temperature = "sensors.t_flow" }

[implements."local/heat_pump@1".members.t_return]
map = { temperature = "sensors.t_return" }

[implements."local/heat_pump@1".members.meter]
map = { p_total = "power.p" }
```

| Key | Type | Req. | Default | Validation |
|---|---|---|---|---|
| `members.<member>` | table with `capabilities`, `map` and `members` (the keys of this section, recursively) | cond. | — | required member without subtable `J0601`; member of a declared capability without subtable `J0602`; `<member>` that is not a class member `J0824` |
| `members.<collection>.<element>` | the same table, one per element; `<element>` is a `snake_case` name | cond. | — | number of elements outside `[min..max]` `J0653`; invalid name `J0824` |

- The submembers **do not get an instance name**: they exist through the nested paths of the device (`hp1.compressor.drive.speed`, document 16, P6). In a collection, the `<element>` acts as the name of the element's instance in the path (`st1.pumps.p1.running`). A nested path equal to that of another signal of the device is `J0604`.
- The recursion stops at the class depth (`JC0501`): at most two levels of `members` below the `[implements]`.
- `members` is a key of this table, and not a member name: the submembers of a class member always go in `members.<member>.members.<submember>`, so that a member called `map` or `capabilities` does not collide with the keys.
- A subtable binds only to points of the profile. A member that should be another device is bound in a composite instance in the manifest (ref/01 §5.13), and not here.

#### 2.2.15 `[discovery]` and the `joker/sunspec@1` profile

```toml
[discovery]
kind   = "sunspec"
bases  = [40000, 50000, 0]
models = [1, 101, 102, 103, 120, 121, 122, 123, 160, 701, 702, 703, 704]

[discovery.names]
"103.W"            = "ac.p"
"103.Hz"           = "ac.f"
"704.WMaxLimPct"   = "w_max_lim_pct"
```

| Key | Type | Req. | Default | Meaning |
|---|---|---|---|---|
| `kind` | `sunspec` | yes | — | the only one in 1.0; `canopen_lss`, `opcua_browse` reserved 1.x (`J0807`) |
| `bases` | list of addresses | no | `[40000, 50000, 0]` | where to look for the `SunS` marker |
| `models` | list of ids | no | all known ones | accepted models; a discovered model outside the list is ignored with a warning |
| `max_models` | integer | no | 64 | |
| `names` | table `"<model>.<point>" → path` | no | — | names of the generated signals; without a name, the path is `m<id>.<point in snake_case>`, and the repeated groups `m<id>.<group>_<n>.<point>` |
| `writable` | list of `"<model>.<point>"` | no | those with RW access in the model | points that become `output` |

- `profile = "sunspec"` in the manifest is the short form of `profile = "joker/sunspec@1"`, the profile **embedded** in the runtime (list of official models, table of names, `implements."inverter.pv@2"`, `fallback` of model 704). The lock always records it by the full form, `[profiles."joker/sunspec@1"]` with `source = "builtin:"` (ref/01 §5.8, ref/02 §2.1.5). A vendor profile may have `[discovery]` and `[signals]` at the same time (fixed points outside the models).
- The scales come from the `*_SF` points as `scale_factor`, read in the same batch (05 §3).
- The result (models, addresses, firmware, digest of the effective map) goes to the lock (`[discovered.<d>]` with the `models` field, which is the `discovered` schema of the Modbus drivers; ref/02 §2.1.11, ref/06 §2.11) and is only used in `prod` if it is pinned (05 §7).
- Invalid configuration: `J0825`.
- **The walk** (ADR 0077) reads only, with FC 3: the marker `SunS` at each of `bases` in order; then each model header (`id`, `len`), the next one at `at + 2 + len`, until the id `0xFFFF` or an exception on a header; then the body of each accepted model the driver knows (1, 101–103, the head of 201–204). No marker, more than `max_models` models, or a failed read: `J0876` at `connect`.
- **The effective map** is `{ models, scales }`: the accepted models in chain order (`at` is the address of the id register) and every `*_SF` read, keyed `<prefix>.<point>`, where the prefix is `m<id>` and `m<id>_<n>` for the n-th repetition of a model. Its digest covers the scale factors, so a changed factor is a drift of the map. A chain whose digest differs from the pinned one fails `connect` with `J0401 kind=map`.
- **Generated profile.** From a map, `jk profile import`-style output (§2.2.19): one input per point of each known model at its absolute address, with type, unit and `label`; the scale factor read at discovery is written as `scale` (this runtime does not read `scale_factor`, ADR 0064), with a `# REVIEW` line. In this runtime, the drivers discover when the device's quirks carry `discovery`, and `[discovery]` in a profile is still refused (`J0807`) until jokerd pins and passes the map (ADR 0077 §8).

#### 2.2.16 Generated profiles (Joker Link)

The `joker-link` driver generates the profile of an MCU from the **catalog** that the `HELLO` announces by its hash (19 §6, ref/07 §6.3). It is a complete profile, in the same model, with `name = "joker/link-<12 hex of the catalog hash>"`, the family `joker/link-*` (§2.2.2) and addressing by the MCU's `SignalId`. It is not written, not published and **does not enter `[profiles]` of the lock**: it is pinned by `[discovered.<d>] digest`, which is the hash of the catalog (ref/02 §2.1.11). `jk explain <device> --profile` shows it in TOML.

#### 2.2.17 Versions of a profile

| Change | Classification |
|---|---|
| address, FC, raw type, byte/word order, scale, offset, dimension of the unit, direction, deleting or renaming a signal, enum variant with another value, deleting an `implements` or a capability | **major** |
| new signal, new variant, new named bit, new action, new `implements` or capability, `limits`/`stuck_detect`/`max_age`, `quirks`, `firmware`, unit of the same dimension | minor |
| `label`, `description`, `docs`, hints | patch |

`jk profile diff <a> <b>` applies the table; `jk profile publish` rejects a version that does not bump what the table requires (`J0848`). There is no inheritance between profiles in 1.0 (`extends` reserved, `J0807`; §5).

```toml
"p_set"    = { at = 40100, fc = 16, type = "i16", scale = 0.1, unit = "kW", direction = "output", readback = "p_set_rb", safe_hint = "0 kW", range_hint = ["-125 kW", "125 kW"] }
"p_set_rb" = { at = 40100, fc = 3,  type = "i16", scale = 0.1, unit = "kW" }
```

#### 2.2.19 Importing a register map in CSV

Most Modbus equipment comes with a register table in a datasheet. `jk profile import csv` turns that table, converted to CSV, into a profile **draft**: it writes everything the table says, and marks with `# REVIEW` what the table cannot say. The draft is a normal profile; it only stops being a draft when someone resolves the `# REVIEW` lines and `jk profile test` passes against the equipment.

```
jk profile import csv <file> --name <vendor>/<model> --driver modbus [--out <file>] [--modicon]
```

| Option | Type | Req. | Default | Validation and meaning |
|---|---|---|---|---|
| `<file>` | path | yes | — | the CSV (format below); `-` reads from stdin |
| `--name` | profile name (§2.1.2) | yes | — | `J0805`; goes to `[profile] name`; `local/<model>` for project profiles that are never published |
| `--driver` | family (§2.2.2) | yes | — | in 1.0, only `modbus` (another family: usage error, exit code 1) |
| `--out` | path | no | `profiles/<vendor>/<model>@1.profile.toml` | the importer **never overwrites**: a file that already exists is a usage error (code 1) |
| `--modicon` | — | no | off | reads the `at` column in the old base-1 notation with the space in front: `0xxxx` coils, `1xxxx` discrete inputs, `3xxxx` input registers, `4xxxx` holding registers (5 or 6 digits: `30002`, `400001`); the importer subtracts the base and checks the space against the `fc` (`J0810`) |

**File format.** RFC 4180, UTF-8 (a BOM at the start is accepted and ignored, because that is what spreadsheets export). The separator is the comma, or the semicolon if the header uses it (the same in the whole file). Numbers always use the decimal point: `0,1` is `J0806`, with the help "use `0.1`". Lines starting with `#` are comments and empty lines are ignored. At most 4,096 data lines (§2.1.5). The order of the lines is the order of the signals in the profile.

**Required header:** the first line that is not a comment. Names in lowercase, in any order, each at most once. `signal`, `fc` and `at` must be present; the other columns may be missing, and an empty cell is the default of the key. Without a header, or without one of the three required columns, it is `J0803` (the file is not a register map); an unknown or repeated column is `J0140`.

| Column | Req. | Empty cell | Validation | Goes to |
|---|---|---|---|---|
| `signal` | yes | — (required in each line) | relative path (§2.1.2, `J0805`); repeated `J0811` | the key in `[signals]` |
| `fc` | yes | — | 1, 2, 3, 4, 5, 6, 15, 16 (`J0810`) | `fc` |
| `at` | yes | — | decimal integer or `0x…`, base 0, 0–65535 (§2.2.5, `J0810`); with `--modicon`, the base-1 notation above | `at` |
| `type` | no | `bool` with FC 1, 2, 5, 15; `u16` with FC 3, 4, 6, 16 | raw type of §2.2.7 compatible with the FC (`J0809`) | `type` |
| `direction` | no | `output` with FC 5, 6, 15, 16; `input` with FC 1, 2, 3, 4 | `input` \| `output` \| `param`; `output` only with a write FC and `input`/`param` only with a read FC (`J0810`) | `direction` (omitted when it is `input`) |
| `unit` | no | `1` | catalog of 16 §5 (`J0109`); forbidden in `bool` (`J0815`) | `unit` |
| `scale` | no | `1` | number ≠ 0 (`J0806`); forbidden in `bool` (`J0815`) | `scale` |
| `offset` | no | `0` | number or quantity (`J0806`, `J0107`) | `offset` |
| `label` | no | — | ≤ 64 B | `label` |
| `description` | no | — | ≤ 1 KiB | `description` |

Each line is validated with the rules of the profile (§2.2.4, §2.2.5, §2.2.7): register overlaps (`J0811`), the FCs per type (`J0809`), the units (`J0109`). The errors come out with the `file:line:column` of the CSV, all of them and not only the first; with errors, nothing is written (exit code 2).

**What the importer infers, and what it leaves to review.** The importer only writes what the CSV says. What is a decision about the equipment, and not a copy of the table, stays in a `# REVIEW: …` comment on the line it concerns:

| Subject | The importer | Stays `# REVIEW` because |
|---|---|---|
| `[profile]` `version` | `"1.0.0"` | — |
| `vendor`, `model`, `docs`, `firmware`, `license` | does not write | the register table does not state them; `license` is required to publish (`J0848`) |
| `quirks` (`max_regs`, `latency`, `forbidden`, `single_write`) | does not write | they depend on the equipment; `jk profile test` measures the latency and suggests `latency` (§4, S9) |
| `[defaults] poll` | `"1s"` | the rate is a project decision |
| `readback` of an output | suggests it when there is an input with the same `at` in a corresponding read FC (FC 5 ↔ 1, FC 6/16 ↔ 3) | it may be just a coincidence of addresses |
| `safe_hint`, `range_hint` of an output | does not write | it is what the equipment accepts and what is safe, and no table states the latter |
| `monotonic` | suggests it on an unsigned integer with a counter unit (`s`, `h`, `Wh`, `kWh`, `MWh`, `m3`) | an operating time is monotonic, a timer is not |
| `limits`, `stuck_detect`, `deadband`, `invalid` | does not write | they belong to the physical behavior of the equipment |
| enums, named bits, `[coherent]`, `[actions]`, `[connect]` | does not write | the CSV has no columns for them |
| `[fallback]` | does not write; leaves a comment at the end | whether the equipment has a communication fallback, and with what time, is in the datasheet, in another section (§2.2.11) |
| notation of the addresses | without `--modicon`, if all the `at` of a register FC are in the range `30001`–`39999` or `40001`–`49999`, it warns | it is the classic sign of a datasheet in base-1 notation |

**Example.** The map of the ESP32 bench firmware (document 23, §4):

```
signal,fc,at,type,direction,unit,scale,offset,label,description
led,5,0,bool,output,,,,LED,board LED (GPIO2)
led_rb,1,0,bool,,,,,,
button,2,0,bool,,,,,BOOT,"BOOT button, already inverted: 1 = pressed"
touch,4,0,u16,,,,,,raw value of touch sensor T0 (GPIO4); drops when touched
rssi,4,1,i16,,,,,,Wi-Fi RSSI in dBm; 0 without connection
uptime,4,2,u32,,s,,,,seconds since boot
fw,3,0,u16,param,,,,,bench firmware version
```

`jk profile import csv map.csv --name local/bench-esp32 --driver modbus` writes:

```toml
# profiles/local/bench-esp32@1.profile.toml
# Generated by jk profile import csv map.csv. Resolve the "# REVIEW" lines and run jk profile test.
schema = 1

[profile]
name    = "local/bench-esp32"
version = "1.0.0"
driver  = "modbus"
# REVIEW: vendor, model, docs, firmware (the register table does not state them)
# REVIEW: quirks: jk profile test measures the latency and suggests quirks.latency

[defaults]
poll = "1s"   # REVIEW: read rate

[signals]
"led"    = { at = 0, fc = 5, type = "bool", direction = "output", label = "LED", description = "board LED (GPIO2)" }   # REVIEW: readback = "led_rb"? safe_hint?
"led_rb" = { at = 0, fc = 1, type = "bool" }
"button" = { at = 0, fc = 2, type = "bool", label = "BOOT", description = "BOOT button, already inverted: 1 = pressed" }
"touch"  = { at = 0, fc = 4, type = "u16", description = "raw value of touch sensor T0 (GPIO4); drops when touched" }
"rssi"   = { at = 1, fc = 4, type = "i16", description = "Wi-Fi RSSI in dBm; 0 without connection" }
"uptime" = { at = 2, fc = 4, type = "u32", unit = "s", description = "seconds since boot" }   # REVIEW: monotonic = true?
"fw"     = { at = 0, fc = 3, type = "u16", direction = "param", description = "bench firmware version" }

# REVIEW: [fallback]: does the equipment have a communication fallback? (ref/03 §2.2.11)
```

Resolving the `# REVIEW` lines of this draft gives the profile of document 23, §4 (`readback`, `safe_hint`, `deadband` on the touch, `monotonic`, `poll = "100ms"` and the 2 s `[fallback]`). The `# REVIEW` comments are not keys: `jk profile check` validates the draft like any profile, and lists the remaining `# REVIEW` lines as notes; `jk profile publish` rejects a file that still has them (`J0848`).

#### 2.2.20 Equipment URIs

The URI tells `jk profile test` (and `jk discover`, document 05 §7) how to reach a piece of equipment **without a manifest**: protocol, port or address, and unit. It goes as it is into the `uri` field of `POST /v1/profile-tests` and `POST /v1/discovery` (ref/09 §5.17). A malformed URI, with an unknown scheme or with an unknown parameter is `J-E1708`, on the laptop and on the node.

| Scheme | Form | Parameters (`?a=b&c=d`) | Defaults | Driver |
|---|---|---|---|---|
| `modbus-rtu` | `modbus-rtu:<port>?baud=<b>&unit=<u>` | `baud` (300–4,000,000, **required**), `unit` (1–247), `parity` (`none` \| `even` \| `odd`), `stop` (1 \| 2), `data_bits` (7 \| 8) | `unit=1`, and the defaults of a `serial` bus (ref/01 §5.6): `parity=none`, `stop=1`, `data_bits=8` | `modbus-rtu` |
| `modbus-tcp` | `modbus-tcp://<host>[:<port>]?unit=<u>` | `unit` (0–255) | port 502, `unit=1` | `modbus-tcp` |
| `sunspec` | `sunspec://<host>[:<port>]?unit=<u>` | `unit` (0–255) | port 502, `unit=1` | `modbus-tcp`, with the `joker/sunspec@1` profile and discovery (§2.2.15) |
| `i2c` | `i2c:<bus>?address=<a>` | `address` (0x03–0x77, **required**, decimal or `0x…`) | — | `i2c` |

- **`<port>`** is an absolute device path (`/dev/serial/by-id/usb-Silicon_Labs_CP2102_USB_to_UART_Bridge_Controller_0001-if00-port0`) or, with `--node`, the name of a port of the `[serial]` of the node's board (`modbus-rtu:uart0?baud=9600`, §2.3.2). It is everything between `modbus-rtu:` and the `?`; the characters `?`, `&`, `#`, `%` and the space are written `%XX`. A port that does not exist is `J0828`. **Always write the `by-id` path**: `/dev/ttyUSB0` changes number when another adapter is plugged in.
- **`<bus>`** of `i2c`: path (`/dev/i2c-1`) or name of the board's `[i2c]` (`i2c1`).
- **`<host>`** is a DNS name, an IPv4, or an IPv6 between `[ ]`. Only in `jk discover`, `<host>` may be a CIDR network (`modbus-tcp://192.168.10.0/24`) and the unit a range (`--unit 1..10`, or `?unit=1..10`); in `jk profile test`, a single piece of equipment and a single unit.
- **There are never credentials in a URI.** A URI with `<user>@` or with a `password` parameter is `J-E1708`. Equipment that needs credentials or transport security (`opcua`, `mqtt`) is tested with a manifest and `jk check --node`, where the credentials are `secret:` (ref/01 §3.10); that is why they have no URI scheme in 1.0.
- The URI does not replace the profile: it only says **where** the equipment is. The keys of the profile (`quirks`, addresses) apply as for a device of the manifest.

### 2.3 Boards

A board profile describes the fixed hardware of a **model** of computer (Linux) or of microcontroller (Joker Micro). It is referred to by `[target] board = "<name>"` (ref/01) and by `jk build --target <name>`.

#### 2.3.1 `[board]`

| Key | Type | Req. | Default | Validation and meaning |
|---|---|---|---|---|
| `name` | string | yes | — | §2.1.2, equal to the file name (`J0804`) |
| `version` | SemVer | yes | — | versions as for profiles (§2.3.6) |
| `os` | `linux` \| `none` | no | `linux` | `none` = Joker Micro |
| `arch` | `aarch64` \| `x86_64` \| `armv7` \| `riscv64` \| `armv6` (Linux; `armv6` only with `tier = "dev"`, document 23); Rust triple (MCU: `thumbv8m.main-none-eabihf`, `riscv32imac-unknown-none-elf`, `xtensa-esp32s3-none-elf`, `xtensa-esp32-none-elf`) | yes | — | inconsistent with `os`: `J0829` |
| `tier` | `"1"` \| `"2"` \| `"dev"` (string) | no | `"2"` | support level (01 §22) |
| `mcu_class` | `m1` \| `m2` | with `os = "none"` | — | 19 §3.1; on Linux: `J0829` |
| `chip` | string | with `os = "none"` | — | the name of the chip **as the HAL writes it** (`"rp235xa"`, `"stm32g474re"`, `"esp32"`, `"esp32c6"`), which `jk build` passes to the HAL as a feature; it decides the `chip-*` family of `joker-micro` (ref/08 §2.11.2, §2.15.1). A chip that no supported HAL knows, or inconsistent with `arch`, is `J0829`; on Linux, `J0829`. It is distinct from `[probe] chip` (§2.3.3), which is the `probe-rs` name |
| `vendor`, `model`, `description`, `docs`, `license`, `authors` | strings | no | — | as in `[profile]` |
| `cpus` | integer | yes on Linux | — | CPU cores |
| `memory` | IEC quantity (`"8 GiB"`) | yes | — | RAM; basis of `J0380` (70%) |
| `flash` | IEC quantity | with `os = "none"` | — | |
| `storage` | `"sd"` \| `"emmc"` \| `"ssd"` | no (Linux only) | `"sd"` (the worst case) | the medium where `/var/lib/joker` lives (historian, WAL, decision log, `kv`, trace). `jk check` projects the write load of the manifest (bytes per day and fsyncs per hour) and compares it with the threshold of the medium; `jk doctor` measures it on the node. Above the threshold, the warning `J0381` with the sources, in order (document 01, §12 and §19). `jk board probe` proposes it from the root device (`/sys/block/<dev>/device/type`: `SD` → `sd`, `MMC` → `emmc`; NVMe or SATA → `ssd`). On an MCU (`os = "none"`): `J0829` |
| `fpu` | `none` \| `sp` \| `sp+dcp` \| `dp` | no | `dp` on Linux, `none` on MCU | the same enum as the firmware descriptor (ref/08 §2.14, key 15; `fpu` in `spec/cddl/joker-micro.cddl`): `none` = no FPU, `f32` and `f64` in software (`J0780` for `f32`, `J0721` for `f64`); `sp` = single precision in hardware, `f64` in software (`J0721`); `sp+dcp` = single precision plus a double-precision coprocessor, like the DCP of the RP2350 (`f64` is accelerated and does not give `J0721`); `dp` = single and double in hardware |

| `stack` | IEC quantity | with `os = "none"` | — | stack available to the node (sum of the active interrupt levels); `jk check` compares it with the stacks measured at build (`J0774`, ref/08 §2.9.3) |
| `clock` | quantity (`"150 MHz"`) | no | — | nominal frequency |
| `recommended` | table `class → list of CPUs` | no | — | suggestion for `[resources]` (01 §2); CPUs outside `0..cpus−1`: `J0829`. With `cpus = 1`, all classes share CPU 0 (`{ rt = [0], io = [0], bg = [0] }`), and that overlap with `rt` is a **note** of `jk check`, not `J0360` (ref/01 §5.4) |
| `kernel` | `preempt_rt` \| `standard` | no | `standard` | kernel with which the board is supported; `jk doctor` compares |
| `boot_cmdline` | list of strings | no | `[]` | suggestions (`isolcpus=3`, `nohz_full=3`) shown by `jk doctor --rt` |

#### 2.3.2 Peripherals on Linux

| Section | Form | Meaning |
|---|---|---|
| `[watchdog]` | `device` (path), `timeout` (duration), `min_timeout`, `max_timeout` | hardware watchdog (01 §8) |
| `[gpio]` | `chip` (label or path: `"pinctrl-rp1"`), `lines` (table `name → offset`, optional; without it, the kernel names are used) | resolves `chip = "auto"` and `line = "GPIO17"` of the manifest; unknown line: `J0828` |
| `[io.<name>]` | `driver`, address of the family (`line`, `var`…), `direction`, `fallback` (value) | fixed IO of the board (LEDs, relays), with the path `board.<name>` (reserved prefix, ref/00 §2); `fallback` is the state that the **hardware** imposes when `jokerd` or the board stops (M1): it counts as the device fallback for that signal, and `J0205` compares it with the `safe` of the manifest like any other. There is no `safe` nor `safe_hint` in a board (ADR 0006; A6) |
| `[serial]` | table `name → path` or `{ path, rs485 = true, max_baud }` | stable serial ports |
| `[i2c]`, `[spi]`, `[can]` | table `name → path` or interface | buses of the board |
| `[net]` | table `name → interface` | interfaces with a stable name |
| `[accel.<name>]` | `kind`, `device` | guaranteed accelerators (`"npu:hailo0"`); **reserved for 1.1** but already accepted (document 11, §"Ready for ML") |

A peripheral name referred to by the manifest that does not exist on the board is `J0828`.

**The fixed IO only exists when it is referred to.** An `[io.<name>]` of the board opens nothing, creates no signals and takes no resources as long as the manifest does not refer to `board.<name>` (in a binding, in an `[outputs."board.<name>"]`, in an instance or in a selector that explicitly catches it; the `**` selector does not count). Once referred to, `jokerd` opens it as an implicit device with the driver and the address of the board. Hence two rules:

- **One kernel resource, one owner.** A device of the manifest that uses the same resource as a referred `board.<name>` (the same LED of `/sys/class/leds`, the same GPIO line of the same `chip`, the same thermal zone) is `J0178` (duplicate address, ref/01 §5.8), like two devices at the same address of a bus. If the `board.<name>` is not referred to, the device of the manifest may use the resource, and the fixed IO does not exist in that generation.
- **The `fallback` of `[io]` only counts through the path `board.<name>`.** It is a hardware fact of that IO, and `J0205` only compares it with the `safe` of `[outputs."board.<name>"]`. A device of the manifest that uses the same resource through another path does not inherit the `fallback`: without its own fallback, it is an output without a device fallback (and `J0205` says so in `prod`).

#### 2.3.6 Versions of a board

Same policy as for profiles: changing a peripheral path, a pin or a partition is **major**; adding peripherals or pins is minor; text is patch. The manifest refers to the board by name (`board = "rpi5"`, which means the highest known major) or with a major (`board = "rpi5@1"`); the lock pins version and digest (ref/02).

#### 2.3.7 Writing a new board

When the `[target] board` of a manifest does not exist in the project nor in the registry (`J0172`, ref/01), you write the board profile. There are three starting points, and the end is always the same file `boards/<board>.board.toml`, validated by `jk board check`:

| Command | Starts from | Useful when |
|---|---|---|
| `jk board probe --node <node> [--name <board>] [--out <file>]` | the inventory of the real node (`GET /v1/node/hardware`, ref/09 §5.2) | the board already has `jokerd` installed and enrolled (this is the normal case) |
| `jk board new <name> --from <board>` | an existing profile, from the project or from the registry | the board is a variant of another (more memory, another radio module) |
| writing by hand | the datasheet | an MCU (`os = "none"`): the flash areas, the interrupt priorities and the capacities are not read from a node |

All three write `version = "1.0.0"`, and **never overwrite** a file that already exists (usage error, exit code 1).

**What `jk board probe` infers, and what is a human decision.** The inventory says what exists **now** on that node. The profile says what the **model** guarantees, and what Joker should expect from it. The probe writes what the inventory proves, and marks with a `# REVIEW: …` comment what only a person can decide:

| Key | The probe writes | From | `# REVIEW` |
|---|---|---|---|
| `name` | `--name`, or the model in lowercase with hyphens (`raspberry-pi-zero-w-rev-1-1`) | `model` | only if it was derived from the model |
| `arch` | the normalized value | `arch` | — |
| `model` | the model, as it is | `model` | — |
| `vendor`, `docs`, `license` | nothing | — | yes: the inventory does not know them |
| `cpus` | the possible CPUs | `cpus.possible` | — |
| `memory` | the power of 2 in MiB above `MemTotal` (`MemTotal` discounts the memory of the GPU and of the kernel: 427 MiB → `"512 MiB"`) | `memory.total` | — |
| `clock` | the maximum frequency | `cpus.max_freq` | — |
| `storage` | the type of the root device (`sd`, `emmc`, `ssd`); nothing when the inventory cannot tell it | `storage.medium` (ADR 0092) | — |
| `tier` | `"dev"` | — | **yes**: the level is a support commitment (01 §22), and `"1"` or `"2"` requires CI with the board |
| `kernel` | `"preempt_rt"` if the current kernel is one, otherwise `"standard"` | `kernel.preempt_rt` | **yes**: it is the **target** kernel with which the board is supported, and not the one installed today |
| `recommended` | a suggestion: with 1 CPU, everything in `[0]`; with 2, `rt = [1]`, `bg = [0]`, `io = [0]`; with 3 or more, `rt` = the last, `io` = the second-to-last, `bg` = the rest | `cpus.count` | **yes**: it depends on what runs on the board besides Joker |
| `boot_cmdline` | `isolcpus`, `nohz_full` and `rcu_nocbs` of the suggested `rt` CPUs (nothing with 1 CPU) | `recommended` | **yes**, with the current boot lines in a comment |
| `[watchdog]` | `device` of the first watchdog; `timeout` = the lower of 15 s and `max_timeout`; `min_timeout`, `max_timeout` | `watchdogs` | — |
| `[gpio] chip` | the `label` of the SoC chip (`pinctrl-*`, or the one with the most lines); the others in a comment, with the lines in use | `gpio_chips` | — |
| `[io.<name>_led]` | one per LED: `driver = "sysfs"`, `led`, `direction = "output"` (`ACT` → `[io.act_led]`) | `leds` | **yes, the `fallback`**: what the LED does by itself when `jokerd` or the board stops. The probe cannot know it; it writes the current `trigger` and leaves the `fallback` line commented out. Without `fallback`, the output has no device fallback, and `J0205` says so in `prod` (§2.3.2) |
| `[io.cpu_temp]`, `[io.<type>_temp]` | one per thermal zone: `driver = "sysfs"`, `thermal` (the zone `cpu-thermal` is named `cpu_temp`) | `thermal_zones` | — |
| `[serial]` | only the UARTs of the board (`soc = true`), by the stable name (`"uart0" = "/dev/serial0"`) | `serial` | USB-serial adapters do **not** go in: they do not belong to the board. They go in a comment, with the `by-id` path, to copy into a `[buses]` of the manifest |
| `[i2c]`, `[spi]` | the ones that exist (`"i2c1" = "/dev/i2c-1"`; `"spi0"` for `spidev0.0`, `"spi0_1"` for `spidev0.1`) | `i2c`, `spi` | if there is none, a comment says that they may be disabled in the boot configuration |
| `[net]` | `"eth"` and `"wifi"` (then `"eth1"`…) for the physical interfaces; never `loopback` nor `virtual` | `net` | — |
| TPM, USB | comments only | `tpm`, `usb` | — (the board does not declare a TPM; `jk doctor` checks it, `J0933`) |

The probe never writes `[gpio] lines` (the kernel names are used), `[accel]` nor `[can]`. If the node already declares a known board (`GET /v1/info`), the probe says so before writing: maybe a new board is not needed.

**Example: the Raspberry Pi Zero W** (the board of the track, part 6). `jk board probe --node zero --name rpi-zero-w` writes:

```toml

recommended = { rt = [0], io = [0], bg = [0] }   # REVIEW: with 1 CPU there is no isolation
# current boot lines: console=serial0,115200 console=tty1 root=PARTUUID=… rootwait

[watchdog]
```

**`jk board check`.** Validates the file with the rules of this section (`J0800`–`J0849`: schema, names, `J0829` for internal inconsistencies). With `--node`, it reads the inventory of the node and confirms, with reads only:

| Check | Against | Failure |
|---|---|---|
| `arch` and `cpus` | `arch`, `cpus.possible` | `J0829` |
| `memory` ≥ `MemTotal` and < 2 × `MemTotal` | `memory.total` | `J0829` |
| `[watchdog] device` exists; `timeout` between `min_timeout` and `max_timeout` of the node | `watchdogs` | `J0828`; `J0829` |
| `[gpio] chip` exists; each `lines` exists; no line of an `[io.*]` `gpio` is in use by the kernel | `gpio_chips` | `J0828`, with the `consumer` that uses it |
| each `[io.*]` `sysfs` exists (`led`, `thermal`) | `leds`, `thermal_zones` | `J0828` |
| each path of `[serial]`, `[i2c]`, `[spi]` exists | `serial` (including `aliases`), `i2c`, `spi` | `J0828` |
| each interface of `[net]` exists | `net` | `J0828` |
| `kernel`, `boot_cmdline` | `kernel`, `cmdline` | does not fail: it is `jk doctor` that compares the target kernel with the installed one; `check` shows the difference as a note |

The remaining `# REVIEW` lines appear at the end as notes, with the line. An example, after having added by hand an `[i2c]` that the node does not have:

```
$ jk board check boards/rpi-zero-w.board.toml --node zero
→ zero (dev) · from --node
error[J0828]: resource nonexistent on the board (line, port, bus, accelerator): `/dev/i2c-1`
  --> boards/rpi-zero-w.board.toml:38:10
   |
38 | "i2c1" = "/dev/i2c-1"
   |          ^^^^^^^^^^^^ node zero does not have this device
   = help: I²C may be disabled (dtparam=i2c_arm=on in /boot/firmware/config.txt); if the board does not guarantee it, remove the line
note: 2 "# REVIEW" lines unresolved (8, 17)
```

**When to publish.** A board in `boards/` of the project resolves before the registry (§3, "Resolution") and enters the lock by the digest of the file, like a published one: for a single project, **there is no need to publish**, and a `tier = "dev"` board normally stays that way (this is the case of the track's `rpi-zero-w`). A `tier = "dev"` board **is never published** (`J0848`, §2.8.4): it is shared as a file (`boards/` of each project, or a common Git repository brought into the project, as a submodule). It is published (`jk board publish`, §2.8.4) when other projects are going to use it, with `tier = "1"` or `"2"`, and only after: all `# REVIEW` lines resolved; `license` written; `jk board check --node` passing on at least one real unit; and `jk doctor` of the node without errors with the declared `kernel`. Publishing a board with `tier = "1"` or `"2"` is also a CI commitment (document 18).

### 2.4 Simulation models

A simulation model is a **simulated device** served by the `sim` driver (04 §6): `[devices.<d>] driver = "sim"`, `model = "sim/<model>.sim.toml"` (ref/01). Its signals appear as `<d>.<signal>`, exactly like those of a real device.

#### 2.4.1 Structure

```toml
schema = 1

[model]        # metadata and integration step (optional)
[params]       # model parameters (optional)
[signals]      # signals
[dynamics]     # equations
[faults]       # scheduled faults and fault keys
[enums]        # as in profiles
[actions]      # simulated actions
[implements]   # as in profiles
[plant]        # plant in Wasm (instead of [dynamics])
```

#### 2.4.2 `[model]`

| Key | Type | Default | Meaning |
|---|---|---|---|
| `description` | string | — | |
| `step` | duration | `"10ms"` | fixed integration and sampling step, in virtual time (and in real time in `jk dev`) |
| `latency` | duration | `"0ms"` | delay between the value of the plant and the delivery of the sample to the core (latency per request, 04 §6) |
| `seed` | u64 integer | derived from the device path (64-bit FNV-1a) | seed of the noise and of the bounce; the scenario may override it |
| `profile` | profile reference (`"<name>@<major>"`, as in `[devices.<d>] profile`) | — | the model **reuses the signals of the profile** (below) |

**`profile`: a model with the signals of a profile.** With `[model] profile = "<ref>"`, the profile is resolved like any other (§3, "Resolution") and stays in the lock in `[profiles]` (ref/02 §2.1.5). The model then has, with the same names, the `[signals]` of the profile with the profile's `type`, `enum`, `unit`, `quantity`, `direction` and `limits`, and it inherits its `[enums]` and `[implements]`. The rest of the profile (addresses, `quirks`, `[config]`, `[fallback]`, `[actions]`, `[connect]`, `[discovery]`) does not apply to a `sim` device. In the `[signals]` of the model:

- an entry with the name of a signal of the profile only adds the simulation keys (`init`, `gen`, `noise`, `resolution`, `bounce`, `latency`, `panel`, `label`, `description`); repeating `type`, `unit`, `direction` or `enum` with another value is `J0815`;
- an entry with a name that the profile does not have is a simulation-only signal, declared in full as without `profile`;
- a signal of the profile without an entry in the model is constant at its `init` (the default of the table below).

This is what allows replacing `driver = "modbus-tcp", profile = "<ref>"` with `driver = "sim", model = "…"` in an overlay without changing the types of the signals nor the instances (document 23, §6.5). A reference that does not resolve to a profile is `J0803`.

#### 2.4.3 `[params]`

Parameters that the manifest gives to the model (`[devices.<d>] params = { … }`, or `sim = { … }` in a class instance, ref/01).

```toml
[params]
mean   = { default = "22 °C" }
amp    = { default = "3 K" }
period = { default = "10m" }
```

| Key of `[params.<name>]` | Type | Req. | Meaning |
|---|---|---|---|
| `default` | value | no | without `default`, the parameter is required |
| `unit` | unit | no | inferred from the `default` |
| `description` | string | no | |

In any value of `init`, `gen`, `noise` and `[faults]`, the string `"$<name>"` is replaced by the parameter. In the expressions of `[dynamics]`, the parameter is `param.<name>`. Unknown parameter, without a value or with the wrong dimension: `J0836`.

#### 2.4.4 `[signals]`

| Key | Type | Req. | Default | Meaning |
|---|---|---|---|---|
| `type` | signal type (02 §2) | yes | — | `enum<Name>` is written `enum = "Name"` with `type` omitted |
| `enum` | name in `[enums]` | no | — | |
| `unit`, `quantity` | as in profiles | no | `1` | |
| `direction` | `input` \| `output` \| `param` | no | `input` | an `output` is written by the core; its value is the **applied** value delivered to the `sim` driver |
| `init` | value | no | `false`, `0` or the first variant | initial state; required in signals with `integrate`, `lag` or `delay` (`J0833`) |
| `gen` | generator (§2.4.5) | no | — | source of the value; exclusive with `[dynamics]` (`J0832`) |
| `noise` | quantity | no | — | additive Gaussian noise (standard deviation) on the generated or computed value |
| `resolution` | quantity | no | — | quantization (ADC) |
| `bounce` | duration | no | — | only in `bool`: each change is delivered with bounce during this time, as edges with an exact timestamp (independent of `step`) |
| `latency` | duration | `[model].latency` | per signal |
| `limits` | `[min, max]` | no | — | physical limits, as in a profile (the plant may go beyond them; acquisition marks `bad(out_of_range)`) |
| `panel` | table (§2.4.7) | no | — | presence in the panel of `jk dev --panel` |
| `label`, `description` | strings | no | — | |

An `input` signal without `gen`, without `[dynamics]` and without `panel` is constant at `init`. An `output` with `gen` or `[dynamics]` is `J0832`.

#### 2.4.5 Generators

`gen = { kind = …, … }`. Bare numeric values are in the unit of the signal; literals with a unit are converted.

| `kind` | Keys (required in bold) | Value at `t` |
|---|---|---|
| `constant` | **`value`** | `value` |
| `step` | **`from`**, **`to`**, **`at`** | `from` before `at`, `to` from `at` on |
| `ramp` | **`from`**, **`to`**, **`over`**, `at` (default `"0s"`) | linear from `from` to `to` between `at` and `at + over`, constant afterwards |
| `sine` | **`mean`**, **`amp`**, **`period`**, `phase` (degrees, default 0) | `mean + amp · sin(2π t/period + phase)` |
| `square` | **`low`**, **`high`**, **`period`**, `duty` (0–1, default 0.5) | |
| `noise` | **`mean`**, **`std`** | Gaussian, seed of the model |
| `walk` | **`start`**, **`std`** (per `step`), `min`, `max` | bounded random walk |
| `replay` | **`file`** (CSV; Parquet is reserved, `J0807`), **`column`**, `time_column` (default `t`), `loop` (bool) | recorded values, step interpolation |

`amp`, `std` and differences use the **difference** unit when the signal is in `°C` (`amp = "3 K"`, 16 §4). Unknown generator or missing key: `J0831`.

**`replay`** reads a CSV with a header row: `time_column` in seconds or as a duration literal, strictly increasing; values bare (in the unit of the signal) or quantities. The value at `t` is that of the last row at or before `t`, and that of the first row before it. With `loop`, the series repeats with a period from the first row to the end of the last, which lasts as long as the interval before it (ADR 0054).

#### 2.4.6 `[dynamics]`

```toml
[dynamics]
level = "integrate((inflow - 0.05 m3/h/% * pump) / 3.2 m2, min = 0 m, max = 3 m)"
```

Each entry `signal = "expression"` defines the value of an `input` signal at each `step`. The language is that of 02 §10 with three extensions, valid **only** here (outside `[dynamics]`: `J0833`):

```
call     := name "(" arg ("," arg)* ")"
arg      := expr | name "=" expr               (named arguments: only in the functions below)
```

| Function | Dimension | Deterministic semantics |
|---|---|---|
| `integrate(d, min = a, max = b)` | `unit(d) · s` = unit of the signal | explicit Euler: `x ← clamp(x + d · step, a, b)`; `min`/`max` optional |
| `lag(u, tau)` | that of `u` | `x ← x + (u − x) · step / tau` |
| `delay(u, t)` | that of `u` | value of `u` `t` ago (ring of `max(1, round(t / step))` samples; `t ≤ 15 min`, `J0305`) |

- The operands are the signals of the model itself (without the device prefix), `param.<name>` and literals. Signals of other devices are not read.
- **Functions that are not in dynamics:** `good`, `quality` and `age` read the quality of an acquired sample, which a plant value does not have: `J0833`. `own` is `J0306`. Every other function and operator of 02 §10 is available, typed as in 16 §4 and ADR 0034 (ADR 0054).
- **Stateful calls** hold their state in the unit of the signal, starting at `init`: `integrate(d)` takes `d` in the difference unit of the signal per second; `lag` and `delay` take `u` in the unit of the signal. They may appear anywhere in the entry and may nest.
- **Order:** at each `step`, first the applied outputs are read, then the stateless expressions are evaluated in the topological order of the dependencies. After the step, every argument of a stateful call is evaluated with the old states, and then all the states (`integrate`, `lag`, `delay`) change at once (explicit Euler, independent of order; ADR 0054). A cycle that does not go through a stateful function is `J0833`.
- Every sub-expression is evaluated at every step, both branches of `if` included (ADR 0034), so a function with memory samples once per step. A window holds `ceil(w / step)` samples and, before it is full, is computed over the samples it has.
- Arithmetic in IEEE 754 `f64` with round-to-nearest; no FMA. The same model gives the same bits on x86_64 and aarch64.

#### 2.4.7 `panel`

| Key | Type | Req. | Default | Meaning |
|---|---|---|---|---|
| `kind` | `lamp` \| `momentary` \| `toggle` \| `slider` \| `gauge` | yes | — | table below |
| `label` | string ≤ 24 B | no | name of the signal | |
| `key` | key | with `momentary`, `toggle` | — | |
| `keys` | `[decrease, increase]` | with `slider`; optional in `gauge` | — | |
| `step` | quantity | with `keys` | — | increment per key |
| `min`, `max` | values | with `slider` | `limits` of the signal | |
| `pulse` | duration | no | `"150ms"` | `momentary`: time at `true` per press |
| `order` | integer | no | order of the file | position in the panel |

| `kind` | Types | Direction | Behavior |
|---|---|---|---|
| `lamp` | `bool`, `enum` | any | shows; never changes the value |
| `momentary` | `bool` | `input` | each press sets `true` during `pulse` (a terminal does not report the key release); key repeat extends it; with `bounce`, the bounce applies |
| `toggle` | `bool` | `input` | each press inverts |
| `slider` | numeric | `input` | the keys add `± step` to the value, between `min` and `max`, and replace the generator |
| `gauge` | numeric | any | shows; with `keys`, adds an **offset** `± step` to the generated value (the generator continues) |

**Keys:** a printable character, or `space`, `enter`, `tab`, `up`, `down`, `left`, `right`, `f1`–`f12`. Reserved by `jk dev`: `q`, `r`, `t`, `?`. Key repeated in the same site (all the models of a manifest), reserved key, or `kind` incompatible with the type or the direction: `J0835`.

#### 2.4.8 `[faults]`

```toml
[faults]
"level" = [{ at = "5m", quality = "bad(comm_failure)", for = "20s" }]
panel   = { key = "f", toggle = "bad(comm_failure)", signals = ["temp", "hum"] }
```

**Scheduled faults:** `"<signal>" = [ fault, … ]`, each one with `at` (instant, required), `for` (duration, required) and **exactly one** effect:

| Effect | Form | Semantics |
|---|---|---|
| `quality` | quality literal | acquisition delivers the signal with that quality: a `bad(…)` carries no value, and an `uncertain(…)` keeps the value the signal had when the fault started, the last good one (ADR 0051) |
| `freeze` | `true` | the value stops changing, with quality `good` (what `stuck_detect` must catch) |
| `value` | value | forced value, with quality `good` (broken sensor lying) |
| `offset` | quantity | added offset |
| `disconnect` | `true` | only in the special key `"*"`: the whole device goes `Down` (05 §12): reads `bad(comm_failure)`, writes fail |
| `delay` | duration | extra latency |

**Fault keys:** the `panel` key (table, or list of tables) with `key`, an effect in toggle form (`toggle = "<quality>"`, `freeze = true` or `disconnect = true`) and `signals` (default: all the `input` signals of the model). That is why `panel` and `"*"` are reserved names in `[faults]`, and a signal named `panel` cannot have scheduled faults (`J0834`). Overlapping faults on the same signal, nonexistent signal or `for ≤ 0`: `J0834`.

**`"*"`** takes every effect: `disconnect` downs the device, and the others apply to every acquired signal. A non-`disconnect` fault on `"*"` counts as a fault on every signal for the overlap rule (`J0834`). Faults on an `output` are `J0834` (ADR 0054).

#### 2.4.9 `[actions]`, `[enums]` and `[implements]`

- `[enums]` and `[implements]` as in profiles (§2.2.8, §2.2.14). The targets of the maps are signals of the model and `"actions.<name>"`.
- `[actions.<name>]` has `args`, `timeout` and `steps`, with the steps `wait`, `fail_if = { signal, equals, message }` and `set = { <signal> = value }` (changes signals of the model; on a signal with `gen` or dynamics, it fixes the value until it is released).
- **Release:** a `set` table with `release = true` releases the signals it names, whose values are ignored: they go back to their generator, dynamics or `init`. A signal named `release` cannot be set.
- The model's actions are **native actions** of the `sim` driver (capability `native-actions`, ref/06 §2.10): the core sends `invoke` with the action's name, and the driver runs the steps against the plant. Other steps are `J0821`, and so is a `wait` beyond the timeout; the timeout of the manifest, when given, wins (17 §4.2). A `fail_if` that matches ends with `device` and its `message`. The arguments arrive as the record of ref/06 §2.10, and a number is in the unit declared in `args` and is converted to the unit of the signal (ADR 0054).

#### 2.4.10 `[plant]`: plant in Wasm

For dynamics that do not fit in `[dynamics]`, a component in the world `joker:sim/plant` (04 §6). Exclusive with `[dynamics]` (`J0832`).

| Key | Type | Req. | Meaning |
|---|---|---|---|
| `component` | `.wasm` path or `oci://…` | yes | |
| `inputs` | list of `output` signals of the model | yes | order of the values delivered to the plant |
| `outputs` | list of `input` signals of the model | yes | order of the values returned |
| `config` | table | no | passed to `init`, in deterministic CBOR |

```wit
package joker:sim@0.1.0;

world plant {
    /// Called once, with the [plant] config table encoded as deterministic CBOR.
    export init: func(config: list<u8>, seed: u64) -> result<_, string>;
    /// Advances the plant by dt-ns of virtual time. Values follow the order of
    /// [plant] inputs and outputs; bool is 0.0 or 1.0, enum is the variant value.
    export step: func(dt-ns: u64, inputs: list<f64>) -> result<list<f64>, string>;
}
```

The plant has no imports (no clock, no randomness, no I/O): it is deterministic by construction. A `step` that returns a number of values different from `outputs`, or an `Err`, puts the device in `bad(device_fault)` and is `J0837` in `jk check` when detectable by the type.

The driver runs the plant through two traits, `PlantEngine` (`init`) and `PlantInstance` (`step`); the Wasm host of the node implements the engine. A build without an engine refuses a model with `[plant]` at `open` with `J0837` (ADR 0054).

#### 2.4.11 Class simulators (reserved 1.0.x)

Class simulators ship in a 1.0.x patch release (document 26, §5; ADR 0035). In 1.0, a `<name>.sim.toml` in a class package is `J0807`, and `[instances.<i>] sim` is `J0290` (ref/01); the `sim` driver with a device model (§2.4.1–§2.4.10) is 1.0.

Each class may bring a simulation model in `classes/<package>/<name>.sim.toml`, with the same schema, `[params]` and an `[implements]` of the class itself. `[instances.<i>] sim = true` uses it with the `default` values; `sim = { … }` passes parameters (ref/01). The instance does not need a device: the runtime creates an internal `sim` device with the name of the instance.

```toml
# classes/std/temp_sensor.sim.toml
schema = 1

[params]
mean   = { default = "22 °C" }
amp    = { default = "3 K" }
period = { default = "10m" }

[signals]
temp = { type = "f64", unit = "°C", gen = { kind = "sine", mean = "$mean", amp = "$amp", period = "$period" }, noise = "0.05 K",
         panel = { label = "Temp", kind = "gauge", keys = ["down", "up"], step = "0.5 K" } }

[faults]
panel = { key = "f", toggle = "bad(comm_failure)" }

[implements."std/temp_sensor@1"]
map = { temperature = "temp" }
```

With several simulated instances of the same class in the same site, the keys collide; `jk dev` assigns them free keys in name order and shows them in the panel, instead of giving `J0835` (the keys of a class simulator are suggestions).

#### 2.4.12 Example: the simulated ESP32 of the track

The model of the bench ESP32 (document 23, §4), as the track defines it in part 4, §5. It uses signals with a panel (`lamp`, `momentary`, `slider`), bounce (`bounce`), noise (`noise`, `resolution`), a generator (`gen`), dynamics (`[dynamics]`) and the panel fault key (`[faults] panel`, §2.4.8), which part 5 uses to disconnect the whole ESP32.

```toml
# sim/esp.sim.toml (track, part 4, §5)
schema = 1

[model]
description = "ESP32 with the bench firmware (document 23, §4)"

[signals]
led    = { type = "bool", direction = "output", panel = { label = "LED ESP32", kind = "lamp" } }
led_rb = { type = "bool" }
button = { type = "bool", init = false, bounce = "5ms", panel = { label = "BOOT", kind = "momentary", key = "b" } }
touch  = { type = "u64", init = 60, noise = 1, resolution = 1,
           panel = { label = "Touch", kind = "slider", keys = ["down", "up"], step = 5, min = 0, max = 100 } }
rssi   = { type = "i64", gen = { kind = "noise", mean = -55, std = 3 } }
```

### 2.5 Scenarios

A scenario is a test of the **site**: the complete manifest, the real core, the real envelope and virtual clock (04 §6). It runs with `jk test`; failing is exit code 6 (07 §8).

#### 2.5.1 `[scenario]`

| Key | Type | Req. | Default | Meaning |
|---|---|---|---|---|
| `name` | string ≤ 256 B | yes | — | |
| `description` | string | no | — | |
| `manifest` | path relative to the project root | no | the input manifest of `jk test` (`--env` or `--manifest`, ref/01 §7.7), otherwise `joker.toml` | |
| `duration` | duration | yes | — | ≤ 30 d; no instant may go beyond it (`J0839`) |
| `seed` | u64 | no | FNV-1a of the `name` | seed of all the models (each model derives its own) |
| `start` | UTC instant RFC 3339 | no | `"2000-01-01T00:00:00Z"` | UTC of instant 0 |
| `clock` | `synced` \| `holdover` \| `unsynced` | no | `synced` | initial quality of the clock |
| `tags` | list | no | `[]` | filter: `jk test --tag` |

#### 2.5.2 Local override

A scenario may adjust the manifest under test, and only this:

| Table | What it may change |
|---|---|
| `[devices.<d>]` | only devices with driver `sim` (or `sim-*`): `model`, `params` |
| `[apps.<a>]` | only `params` |

Any other root table is `J0140`. The goal is to test the same site with another plant, and not to test a different site. `sim-camera` and the stream devices belong to 1.1 (`J0807`).

#### 2.5.3 Actions

All actions have `at` (instant, required). The targets are site paths after the aliases.

| Action | Keys | Semantics |
|---|---|---|
| `[[set]]` | `signal`, **one** of `value` or `series` (generator of §2.4.5, with time counted from `at`), `for` (optional) | replaces the source of the simulated signal; with `for`, the original source comes back at the end |
| `[[press]]` | `signal`, `for` (default `"150ms"`) | `true` during `for`, with the `bounce` of the model; only in `bool` |
| `[[inject]]` | `signal` (signal or selector) or `device`, `for` (req.), an effect of §2.4.8 (`quality`, `freeze`, `value`, `offset`, `delay`; `disconnect` only with `device`) | fault during an interval |
| `[[write]]` | `output`, `value`, `ttl` (req., A10), `level` (default `"manual:4"`), `reason` | manual write, like `jk write` |
| `[[release]]` | `output`, `level` | like `jk release` |
| `[[call]]` | `method` (`"<instance>.<method>"`), `args`, `ttl`, `level` | like `jk call` |
| `[[action]]` | `action` (`"<device\|instance>.<action>"`), `args`, `key` (default: id of the action in the scenario) | like `jk action`; the result is observable with `result` (§2.5.4) |
| `[[app]]` | `app`, `do` (`stop` \| `start` \| `restart`) | lifecycle (track 1, §10) |
| `[[ack]]` | `alarm` | acknowledges an alarm |
| `[[reset]]` | `output`, `reason` | leaves a trip (`jk reset`) |
| `[[clock]]` | one of `quality` (`clock_quality`) or `jump` (signed duration, `"+5s"`, `"-2s"`) | quality of the clock, or a jump of UTC (the monotonic clock never jumps) |

`set`, `press` and `inject` on signals that are not from a `sim` device, or nonexistent targets: `J0838`.

#### 2.5.4 Expectations `[[expect]]`

**When** (exactly one):

| Key | Form | Semantics |
|---|---|---|
| `at` | instant | the state after the last tick of the owning group with `t_tick ≤ at` |
| `during` | interval | in all the ticks of the interval |
| `within` | interval | in at least one tick of the interval |
| `before` | instant | ≡ `within = "0s .. <before>"` |

**What** (exactly one subject):

| Key | Form |
|---|---|
| `signal` | path or selector (inputs, outputs, `calc.*`, members of instances) |
| `alarm` | name of the alarm |
| `instance` | name of the instance (for `health`) |
| `action` | id of an `[[action]]` of the scenario (for `result`) |
| `metric` | reserved for 1.1 (`J0807`) |

**Predicates** (at least one; `J0840` with none or with incompatible ones):

| Predicate | With | Semantics |
|---|---|---|
| `equals` | `signal` | equal value, after unit conversion; `tolerance` (quantity) optional, default 0 |
| `min`, `max` | numeric `signal` | inclusive limits; combinable with each other, but not with `equals` |
| `quality` | `signal` | `"bad"` matches only the code; `"bad(comm_failure)"` matches code and reason |
| `outcome` | `signal` that is an output | the result of the write in the tick (ref/00 §4.4); `"rejected"` matches any reason |
| `level` | `signal` that is an output | active level of the arbiter, or `"none"` |
| `toggles` | `bool` `signal`, with `during` | exact number of changes in the interval |
| `toggles_every` | `bool` `signal`, with `during` | tolerance; all the intervals between complete changes within the interval match (the first and the last, partial, do not count) |
| `pattern` | `bool` `signal`, with `during` | `"on 100ms, off 100ms, …"`: the sequence repeats cyclically from the first change in the interval; `tolerance` (duration) optional, default 1 period of the owning group |
| `state` | `alarm` | `alarm_state` |
| `active` | `alarm` | bool |
| `health` | `instance` | `ok` \| `degraded` \| `failed` |
| `result` | `action` | `ok` \| `err` \| `"err(<reason>)"` |

`equals`, `min`/`max`, `quality`, `outcome` and `level` combine with each other (all must match: `equals = "0 kW"` with `outcome = "rejected(interlock)"` is example 01). `toggles`, `toggles_every` and `pattern` are mutually exclusive and only with `during`. An expectation that fails is `J0842`, with the instant, the value seen and the decision chain (`jk trace`) in the report.

#### 2.5.5 Example

```toml
# sim/scenarios/room.scenario.toml
schema = 1

[scenario]
name     = "steady below the limit, blinks above, fault pattern without sensor"
manifest = "joker.sim.toml"
duration = "90s"

[[press]]
signal = "panel.button"
at     = "1s"
for    = "100ms"

[[set]]
at     = "0s"
signal = "panel.pot"
value  = "1.65 V"

[[set]]
at     = "0s"
signal = "room.temp"
series = { kind = "ramp", from = "22 °C", to = "32 °C", over = "60s" }

[[expect]]
during = "2s .. 15s"
signal = "panel.led"
equals = true

[[inject]]
at      = "70s"
signal  = "room.temp"
quality = "bad(comm_failure)"
for     = "15s"

[[expect]]
during  = "71s .. 84s"
signal  = "panel.led"
pattern = "on 100ms, off 100ms, on 100ms, off 1700ms"

[[expect]]
at    = "84s"
alarm = "room_hot"
state = "unknown"
```

### 2.6 Conformance cases

A single schema for the four batteries: that of the **core** (16 §8, runs against `joker-core` with a virtual clock, on Linux and on an MCU), that of the **classes** (14 §7.3, runs against an instance, in simulation or on a device), that of the **drivers** (ref/06 §6, runs against an N, W or X driver and a double of the equipment) and that of the **actions** (ADR 0066, runs the runtime's device and instance actions against a register double, on Linux). What differs is the *fixture*; the timeline (`do`, `expect`), the literals and the predicates are the same.

#### 2.6.1 Common envelope

```toml
schema = 1

[suite]          # identification and global fixture
# core fixture: [[signals]] [[outputs]] [[writers]] [[atomic]] [[alarms]] [[calc]] [[instances]]
# driver fixture: a separate <driver>.fixture.toml file, passed with --fixture (ref/06 §6.2)
[[case]]         # one or more cases
```

| Key of `[suite]` | Type | Req. | Default | Meaning |
|---|---|---|---|---|
| `kind` | `core` \| `class` \| `driver` \| `action` | yes | — | must agree with the location of the file (`conformance/<area>/`, `classes/`, `conformance/drivers/` or `conformance/actions/`, `J0845`); `driver`: actions, subjects and fixture in ref/06 §6.2–§6.3; `action`: the device and instance actions of the runtime against a register double, and again with the real `modbus-tcp` driver against a wire double (a case limits itself with `doubles`), fixture, actions and expectations in ADR 0066 §20–§24 and ADR 0073 (`linux` host only) |
| `id` | id | yes in `core` and `driver` | in `class`, the reference of the class | prefix of the case ids in the reports |
| `class` | class reference | yes in `class` | — | equal to the file (`classes/std/pump.conformance.toml` → `std/pump@<major of the .jkc>`, `J0845`) |
| `spec` | list of references (`"16 A7"`, `"01 §7 step 5"`) | no | `[]` | traceability |
| `period` | duration | yes in `core` | in `class`, the period of the instance's owning group; does not apply to `driver` | period of the group of the case |
| `hosts` | list: `linux`, `mcu` | no | both | where the case must give the same bytes (ADR 0020) |
| `requires` | list of capabilities | no (`class`, `driver`) | `[]` | the whole suite only runs on instances with these capabilities (in `driver`, capabilities of the descriptor, ref/06 §2.13) |
| `classes` | list of `.jkc` paths | no (`core`) | `[]` | the classes of the `[[instances]]` of the core fixture (§2.6.2) |
| `tiers` | list: `n`, `w`, `x` | no (`driver`) | the three | where the driver suite runs |
| `description` | string | no | — | |

| Key of `[[case]]` | Type | Req. | Default | Meaning |
|---|---|---|---|---|
| `id` | id | yes | — | unique in the suite (`J0805`) |
| `name` | string | no | — | free text for humans |
| `spec` | list | no | `[]` | |
| `requires` | list of capabilities | no | `[]` | in `class`: case skipped (`J0846`, warning) if the instance does not have them; in `driver`: `skip` if the descriptor does not declare them |
| `level` | `basic` \| `full` | no (`driver`) | `basic` | level of the driver case (ref/06 §6.4) |
| `sim_only` | bool | no (`class`) | `false` | the case needs **exclusive ownership** of the instance: that no other writer proposes on the `out` members that the case observes (for example, "the lease expires and the output goes to `safe`"). It only runs on a simulated instance; on a real instance, `jk class verify` does not run it and reports it `skipped (sim_only)` (§2.6.3). In `core` and `driver`, `J0140` |
| `duration` | duration | no | last instant of the case + 1 period | |
| `do` | list of actions | no | `[]` | §2.6.2 and §2.6.3 |
| `expect` | list of expectations | yes | — | §2.6.4 |

Each case starts in a clean state: new generation, all outputs at `safe` (A8), no active writer, alarms in `normal`, clock `synced` (ADR 0042).

#### 2.6.2 Core fixture and actions

The fixture uses the **manifest syntax** (ref/01), in lists:

| Table | Keys | Notes |
|---|---|---|
| `[[signals]]` | `path`, `type`, `unit`, `quantity`, `enum` (`{ Name = { … } }` inline), `max_age` (default: never ages) | inputs used in interlocks and expressions |
| `[[outputs]]` | `path`, `type`, `unit`, and all the keys of `[outputs.*]` (03 §6) | |
| `[[writers]]` | `id`, `level` (`"band:n"`), `lease`, `kind` (`cycle` \| `async` \| `manual` \| `bridge` \| `impl`; `proposal` reserved 1.1), `ttl` (req. with `manual`, A10) | A1 |
| `[[atomic]]` | `id`, `outputs`, `order`, `commit`, `on_rate` | 02 §7.3 |
| `[[alarms]]` | `id`, and the keys of `[alarms.*]` | |
| `[[calc]]` | `path` (`calc.<name>`), `expr` | |
| `[[instances]]` | `name`, `class`, `map`, `capabilities`; the class comes from `classes = [...]` in `[suite]` (`.jkc` paths) | for the cases of methods and queries |

**Actions** in `do` (each one with `at`, a multiple of `period`: `J0843`):

| Action | Form | Semantics |
|---|---|---|
| input | `{ at, input = "<path>", value, quality }` | new sample in the latch of tick `at` (`quality` default `"good"`; `value` may be missing with `bad`); it holds until the next one |
| proposal | `{ at, propose = "<output>", writer, value }` | proposal of the writer in that tick; `async` enters at step 2, `cycle` at step 4 (16 §8) |
| method | `{ at, method = "<instance>.<method>", writer, args }` | method record (17 §4.1) |
| release | `{ at, release = "<output>", writer }` | end of a manual write |
| reset | `{ at, reset = "<output>" }` | end of trip (E7) |
| clock | `{ at, clock = "<clock_quality>" }` | |
| generation | `{ at, generation = "same" }` | swap to an identical generation at that tick boundary (A8) |

The proposals and releases of `async`, `manual` and `bridge` writers enter at step 2; those of `cycle` and `impl` writers, at step 4; within each step, in the order of the case. At a tick boundary: the generation swap, the `clock` actions, the `input` samples, the `reset` actions, and only then the latch. The new generation starts with no active levels and inherits the last applied value (A8); the input samples are kept (ADR 0042).

Unknown writer, output, instance or method: `J0844`.

#### 2.6.3 Class actions

The suite runs against **one** instance (`jk class verify <class> --instance <i>`). The runner is a single writer, `test:<suite>`. On a **simulated** instance (simulator of the class, or composed only of `sim` signals), it writes at level `control:12`, with `lease` = 3 × period. Each proposal of its own is **held**: the runner proposes it again in each tick until it replaces, releases or lets it expire, as an app that writes in each tick would do.

**On a real instance** (any other), the runner actuates equipment, and the rules change:

1. It requires `--allow-actuation` (without it, `J0640`) and `mode = "dev"` in the active generation of the node.
2. Before the first case, the node checks the levels of the instance's `out` members: if any has an active `safety` or `manual` level (from a safety app, from a person, from an approved intent), it rejects the suite with `J0641` and says who holds it. There is no `--takeover`: whoever is in `manual` or `safety` has priority over a test.
3. The runner writes as a manual write of the principal that runs the command (`user:<id>`, `kind = manual`, with `on_behalf_of = test:<suite>` in the decision log), at level **`manual:3`**, with a TTL equal to the **duration of the suite** (the largest `at` of the cases plus the deadline of the expectations, plus 10 s). Proposals are held as above; the TTL is the lease, and it is renewed at each case. If `jk` or the connection drops midway, the level expires by itself at the end of the TTL.
4. **The apps keep running.** The writers that `manual:3` overrides are `overridden` during the test (and take control again when the level is released, at the end of the suite or of the TTL), and the envelope of the site keeps applying to each write of the runner (interlocks, ranges, rates). A `lease_expire` on a real instance releases the `manual:3` of that member, and the value passes to the next active level, and not necessarily to `safe`: the cases that expect `safe` are skipped if there is another active level (`J0846`).
5. If a `safety` or `manual` level of another principal becomes active during the suite, the case in progress fails, the suite stops, and the runner releases its levels (the report says why).
6. **The `sim_only = true` cases do not run.** On a real instance, the runner does not have exclusive ownership of the members: the apps keep proposing below `manual:3` (rule 4), and a case that expects "with no one in control, the output goes to `safe`" would see the value of the app, and not `safe`. Instead of letting it fail, or stopping the apps, the suite marks it: the report lists it as `skipped (sim_only)`, counts it among the skipped ones, and it does not affect the exit code. A case without the mark that depends on this falls under rule 4 (`J0846`, if there is another active level) or fails; that is why whoever writes the suite marks the `lease_expire` cases whose expectation is `safe` or `level = "none"`. On the simulated instance, the `sim_only` cases run like the others.

| Action | Form | Semantics |
|---|---|---|
| method | `{ at, method = "<method>", args }` | call by the test writer |
| proposal | `{ at, propose = "<out member>", value }` | direct write on a member |
| action | `{ at, action = "<action>", args, key }` | invocation (async) |
| expire | `{ at, lease_expire = "<out member>" }` | the writer stops proposing and the lease expires **in that tick** (the effective value becomes `safe` in the latch of that tick, 16 A2 and A6). The `safe` belongs to the site and not to the class: if the `safe` of the member in the instance differs from the `@safe_hint` of the class, the cases that use `lease_expire` on that member are skipped (`J0846`) |
| input | `{ at, input = "<in member>", value, quality }` | only if the instance is simulated (simulator of the class or composed of `sim` signals); on another instance, the case is skipped (`J0846`) |

Nonexistent member, method or action: `J0844`.

#### 2.6.4 Expectations

| Key | Core | Class | Form |
|---|---|---|---|
| when | `at`, `during` | `at`, `during`, `within`, `before` | §2.5.4; in the core, `at` and the bounds of `during` aligned with `period` (`J0843`) |
| subject | `output`, `signal`, `alarm` | `member`, `query`, `health` (bool `true` = check the instance), `event`, `action` | paths (core) or names relative to the instance (class) |
| predicates | `equals`, `min`, `max`, `tolerance`, `quality`, `outcome`, `level`, `state`, `active` | the same, plus `health` (`ok` \| `degraded` \| `failed`), `count` (occurrences of an `event`), `fields` (fields of the last event), `result` | |
| combinators | `any_of`, `all_of` (lists of complete expectations) | same | |

- `equals` on an output is the **applied value** in the tick; the result of the write is `outcome`; the active level is `level` (`"none"` without an active writer).
- In a core case, **each** output of the fixture has, in each tick that the case covers, a result. The runner compares only the ticks and the outputs with an expectation, and the report includes the complete sequence (the determinism gate of 16 §7 compares it byte by byte between hosts).
- Failed expectation: `J0842`.

### 2.7 Class packages

A class package is a directory `classes/<package>/` with a `<package>.package.toml` (the last segment of the package name: `classes/acme/water/water.package.toml`), the `.jkc` files, the conformance suites and the class simulators.

```
classes/acme/water/
  water.package.toml
  valve.jkc                   (one class per file; `valve@2.jkc` if two majors coexist)
  valve.conformance.toml
  valve.sim.toml
```

- The name of the companion files is the **same** as that of the `.jkc`: `<name>.jkc` ↔ `<name>.conformance.toml` ↔ `<name>.sim.toml`. With two majors in the same directory, `<name>@<major>.jkc` and the companions with the same suffix.
- One `.package.toml` file per package directory, with the name of the last segment; another name, or two files, is `J0847`.
- The `local` package does not need a `local.package.toml` and is never published.

```toml
# classes/acme/water/water.package.toml
schema = 1

[package]
name        = "acme/water"
description = "Equipment classes for water networks"
license     = "Apache-2.0"
authors     = ["Automation team <automation@example.com>"]
repository  = "https://git.example.com/acme/joker-classes"
joker       = "1.0"

[dependencies]
"std/pump" = "1.2"
```

| Key | Type | Req. | Default | Validation |
|---|---|---|---|---|
| `name` | package | yes | — | equal to the directory (`J0847`); `std` and `local` reserved (§2.1.2) |
| `description` | string ≤ 1 KiB | no | — | |
| `license` | SPDX expression | yes to publish | — | `J0848` |
| `authors` | list | no | `[]` | |
| `repository`, `homepage`, `docs` | URL | no | — | they go to the OCI annotations |
| `joker` | `"M.m"` | no | `"1.0"` | minimum runtime version for all the classes of the package |
| `jkc` | integer | no | `1` | version of the `.jkc` language |
| `[dependencies]` | table `<package>/<class> → "M.m"` | no | `{}` | **minimum** version of each class used with `use` (within the major that the `use` indicates); a class used without an entry accepts any minor; the lock pins the exact one (ref/02) |

The package **has no version of its own**: the unit of versioning and of publication is the class (`valve@2.1.0`, document 17, §9). The `<package>.package.toml` gives the shared metadata and the dependencies. A `use` for a class that is neither in the registry nor in the project is `J0847`.

### 2.8 Publication to the Hub (OCI)

All catalog artifacts are OCI artifacts (OCI Image Manifest 1.1, with `artifactType`), signed by the role of ref/00 §7.1 (`profiles`, `boards`, `classes`). The media types are those of the single table of ref/00 §7.1 (D13): the short form (`joker.profile.v1+toml`) and the full form (`application/vnd.joker.profile.v1+toml`). The table below only says in which layers they go.

#### 2.8.1 Repositories and tags

| Artifact | Repository | Tags |
|---|---|---|
| profile | `<registry>/<prefix>/profiles/<vendor>/<model>` | `<version>` (immutable) and `<major>` (movable) |
| board | `<registry>/<prefix>/boards/<board>` | same |
| class | `<registry>/<prefix>/classes/<package>/<name>` | same |

Example: `registry.example.com/joker/profiles/eastron/sdm630:1.2.0`. The lock always pins the **digest**; the tags are only for discovery. Republishing an existing version with other content is rejected (`J0848`).

#### 2.8.2 Media types and layers

| Artifact | `artifactType` | Layers (in this order) |
|---|---|---|
| profile | `application/vnd.joker.profile.v1+toml` | the profile file (`application/vnd.joker.profile.v1+toml`); optional: a simulation model of the equipment (`application/vnd.joker.sim.v1+toml`) |
| board | `application/vnd.joker.board.v1+toml` | the board file (`application/vnd.joker.board.v1+toml`) |
| class | `application/vnd.joker.class.v1+jkc` | `.jkc` (`application/vnd.joker.class.v1+jkc`); contract (`application/vnd.joker.class.contract.v1+json`); conformance (`application/vnd.joker.class.conformance.v1+toml`); optional: simulator (`application/vnd.joker.sim.v1+toml`); `<package>.package.toml` (`application/vnd.joker.class.package.v1+toml`) |
| conformance report | `application/vnd.joker.conformance-report.v1+json` | the report (JSON), with `subject` = the verified artifact (*referrer*) |

- The `config` of the OCI manifest is the empty descriptor (`application/vnd.oci.empty.v1+json`, content `{}`).
- Each layer carries `org.opencontainers.image.title` with the file name, **with the type suffix** (`sdm630@1.profile.toml`, `rpi5.board.toml`, `valve.sim.toml`, `water.package.toml`): the `jk` that downloads a layer saves it with that name, and the check of §2.1.6 also applies to what comes from the registry. A layer whose title does not have the suffix of its media type is rejected on publication (`J0848`) and on installation (`J0803`).
- The signatures (cosign or notation) and the conformance reports are *referrers* of the artifact.
- The **digest that the lock pins** for a profile or a board is that of the layer of the TOML file (sha256 of the bytes of the file). It is the same for a local file and for the published artifact, and so moving from `profiles/` to the registry does not change the lock.

#### 2.8.3 Annotations

In the OCI manifest (values always strings):

| Annotation | Profile | Board | Class | Value |
|---|---|---|---|---|
| `org.opencontainers.image.title` | yes | yes | yes | name (`eastron/sdm630`) |
| `org.opencontainers.image.version` | yes | yes | yes | SemVer |
| `org.opencontainers.image.description` | if present | if present | if present | |
| `org.opencontainers.image.licenses` | yes | yes | yes | SPDX |
| `org.opencontainers.image.authors` | if present | if present | if present | comma-separated |
| `org.opencontainers.image.source`, `.revision`, `.created`, `.vendor`, `.url`, `.documentation` | optional | optional | optional | |
| `joker.kind` | `profile` | `board` | `class` | |
| `joker.schema` | `1` | `1` | — | |
| `joker.min_runtime` | `joker` | `joker` | `joker` of the package | `"1.0"` |
| `joker.major` | yes | yes | yes | |
| `joker.driver` | yes | — | — | family |
| `joker.implements` | if present | — | — | comma-separated class references, sorted |
| `joker.arch`, `joker.os`, `joker.mcu_class` | — | yes | — | |

#### 2.8.4 Publication checks

| Command | Checks | Error |
|---|---|---|
| `jk profile publish` | `jk check` of the profile, `license`, namespace, `jk profile diff` against the last published version of the same major, conformance report of **each** `implements` | `J0848`, `J0849` |
| `jk class publish` | `jkc check`, `license` of the package, `jk class diff` (17 §9), the suite itself passing against the class simulator (if there is one) or against an indicated implementation | `J0848`, `J0849` |
| `jk board publish <file>` | `jk board check` of the file, `license`, no unresolved `# REVIEW`, version not yet published and bumped as §2.3.6 requires, and `tier` `"1"` or `"2"`: **a `tier = "dev"` board is never published to the Hub** (nor to an organization OCI registry, which has the same checks) | `J0848` |

The conformance report is produced by `jk class verify … --report <file>` and signed by whoever publishes. In 1.0, the Hub accepts `evidence = "sim"` for classes and requires `evidence = "hardware"` for profiles (the profile says what a real piece of equipment does). Report missing, failed, of another version or not signed: `J0849`.

## 3. Expected behavior

**Validation.** Everything in §2 is checked in `jk check` without I/O: the catalog and simulation files referred to by the manifest, the scenarios of `sim/scenarios/` and the suites. The `plan` of the driver (pure) validates the addressing and the coherence; an error of `plan` carries the code of §2.9 and the location in the file. The validation order is: TOML → `schema`/`joker` → keys (`J0140`) → literals → references → domain rules. All errors are reported, not only the first, in file and line order.

**Resolution.** A profile `<name>@<major>` is resolved in this order: `profiles/` of the project (the file `profiles/<name>@<major>.profile.toml`; a board, `boards/<board>.board.toml`; §2.1.6); the entries of the search path of the client configuration, in order (`defaults.search`, ref/02 §2.3.2), in which `"builtin:"` are the embedded ones (`joker/…`) and, without it in the list, the embedded ones come at the end. By default, the path is `["builtin:", "<official Hub>"]` (in the examples, `oci://hub.example.com/joker`). Two candidates with the same name and major in different sources is `J0805` (ambiguity is an error), unless the lock pins one. The same holds for boards and classes.

**Acquisition.** The order of application of a raw point, in the acquisition stage (01 §3.3): decoding (type, `word_order`, `byte_order`, `bit`, `invert`) → `invalid` → `scale_factor`, `scale`, `offset` → conversion to the canonical unit → NaN (`bad(nan)`) → `limits` (`bad(out_of_range)`) → `enum` (`bad(out_of_range)` without a variant) → `deadband` → `stuck_detect` → link quality (05 §12). The first one that marks `bad` decides the reason.

**Simulation.** The `sim` driver is deterministic: with the same manifest, the same models, the same seed and the same scenario, the sequence of samples and of results is bit-for-bit equal on any host. The clock is the virtual clock of `jk test` (ADR 0007); in `jk dev`, the same step runs in real time. The actions of a scenario at the same instant are applied in file order, before the latch of the groups with `t_tick = at`.

**Conformance.** The expected values are written by hand (16 §8, the Cravo rule). The runner does not "correct" expectations nor interpolate: a case passes or fails. In the core, the complete sequence of results of each case is the artifact that is compared between Linux and MCU.

**Compatibility.** `schema = 1` covers the whole 1.x series. In a minor, only optional keys, enum values at the end and new sections are added (ref/00 §1). A file that uses a key of a minor declares `joker = "1.<minor>"`; `jk check` warns if the key used requires a minor above the declared one, so that the error appears to whoever writes and not to whoever installs (§4, S1). A `schema = 2` only in v2, with `jk migrate`.

**Safety.** Profile actions do not go through the envelope (they are actions), but they go through the permissive and the role of the manifest (17 §4.2) and are recorded in the decision log. The `[connect]` and `[relinquish]` steps are also recorded. A profile must not declare `safe`: only `safe_hint` (ADR 0006). `jk class verify` against an instance that is not simulated requires `--allow-actuation` (`J0640`), only runs with `mode = "dev"` on the node, refuses to run with a `safety` or `manual` level active on the outputs of the instance (`J0641`), and the test writer writes at `manual:3` with a TTL equal to the duration of the suite and goes through the arbiter and the envelope of the site like any other (§2.6.3).

**Dependencies on other references** (checked field by field in this round):

| Reference | What is coherent |
|---|---|
| ref/01 | `[devices.<d>]`: `profile` (`<name>@<major>`, or `sunspec` ≡ `joker/sunspec@1`), `model` and `params` (driver `sim`, §2.4), `config` (§2.2.10), `discover` (§2.2.15), `fallback.configure` (§2.2.11); `[instances.<i>] sim = true \| table` (§2.4.11); `[target] board = "name" \| "name@major"` (§2.3.6); signal adjustments with the same grammar (§2.2.4, including `scale = { from, to }`); address keys of drivers without a profile equal to those of §2.2.5 (appendix A of ref/01); fixed IO of the boards with `fallback` |
| ref/02 | lock: `[profiles."<name>@<major>"]` and `[boards."<value of board>"]` with `resolved` and `digest` = SHA-256 of the bytes of the file (§2.8.2); `[classes."<ref>"]`; `[discovered.<d>]` with `models` in SunSpec profiles; `[fallback.<d>]` field by field with §2.2.11; `[mcu.<d>] capacity` with the names of `[capacities]`; registry search path (`defaults.search`) |

## 4. Stress

**S1 — A profile from the Hub uses a key of 1.3; the node is on 1.1.** With nothing else, the node would give `J0140` "unknown key", which looks like a typo. **Broke.** **Fix incorporated:** `joker = "1.3"` in the file gives `J0802` with the requested version; the `joker.min_runtime` annotation lets the Hub and `jk lock` choose the latest compatible version; the `jk check` of whoever writes warns if the key used requires a minor above the declared one.

**S2 — A SunSpec inverter with the scale in a separate register.** If `W` and `W_SF` came from different requests, the new value could be read with the old scale (05 §3). **Holds:** `scale_factor` makes the pair coherent by construction, and `plan` fails with `J0813` if it does not fit in one request.

**S3 — Two profiles define `PcsState` with different numbers.** `permit = "pcs.state == PcsState.fault"` could resolve to the wrong enum. **Holds:** the enum has profile scope, the literal is resolved by the type of the operand, and a literal without a typed operand with two candidates is `J0303` with the list.

**S4 — Whoever writes copies `Bad(CommFailure)` from `jk status`.** Rejecting it would be pedantic; accepting everything would mean losing control of the grammar. **Holds:** the display form is an exact synonym with a total translation (§2.1.3), `jk fmt` normalizes, and any other spelling is `J0806`.

**S5 — `at = "2m+1.2s"` against "there are no compounds" (ref/00 §3.1).** It **broke** the convention, and rightly so: in a scenario the instant reads as "after the fault, plus 1.2 s". **Fix incorporated:** sums with `+` only in the instant positions of the timeline (scenarios and cases); everywhere else, they remain forbidden. ref/00 §3.1 already says so (resolved).

**S6 — The same scenario gives different results on the laptop and in CI.** Noise, bounce and `walk` use randomness. **Holds:** fixed seed derived from the name of the scenario and from the device path, explicit Euler in `f64` without FMA, defined evaluation order (§2.4.6), Wasm plants without imports. `jk test --seed` reproduces a failure found by `--fuzz`.

**S7 — `jk class verify pump@1 --instance vfd1` on a real site.** It starts a pump for real. **Broke.** **Fix incorporated:** `--allow-actuation` required outside simulated instances, only in `mode = "dev"`, and the test writer goes through the envelope of the site (interlocks and ranges remain in control).

**S8 — A class of outputs only (`status_light@1`).** There is nothing to observe besides the `out` members themselves. **Holds, with a declared boundary:** conformance checks the contract (expansion, atomicity, `safe` after the lease); the behavior of each implementation belongs to its own tests (§2.6.5).

**S9 — Fifteen meters on an RS-485 with profiles without `latency`.** The bus budget (`J0370`) depended on a number that nobody wrote. **Holds:** `quirks.latency` has a default of 10 ms (the value of 05 §5), and `jk profile test` measures the real latency and suggests the value.

**S10 — Republishing `sdm630:1.2.0` with a corrected register.** A site with the old lock would start reading another map with the same version. **Holds:** immutable versions in the Hub (`J0848`), digest of the file in the lock, and `jk profile diff` forces bumping at least the patch.

**S11 — A momentary button in a terminal.** Terminals do not report the key release, and "`true` while pressed" cannot be implemented. It **broke** what 04 §6 suggested. **Fix incorporated:** `momentary` is a pulse of `pulse` (150 ms) per press, extended by key repeat; the bounce applies on top.

**S12 — A CANopen drive with 3,000 parameters.** A profile with all of them in the cycle would exhaust the bus. **Holds:** `direction = "param"` implies `poll = "on_demand"` (05 §3), the limit of 4,096 signals per profile covers a real OD, and `jk profile import eds` already generates them that way.

## 5. Decisions and rejected alternatives

| Decision | Rejected alternative | Why |
|---|---|---|
| the type of the file is in the name suffix (`.profile.toml`, `.board.toml`, `.sim.toml`, …), checked against the content (`J0803`), and in the Hub in the media type (ADR 0026) | the type comes from whoever refers to it (the earlier decision of this reference); a `kind` key in each file | with the type only in whoever refers to it, an `esp.toml` cannot be understood in a listing nor in a review; a `kind` key may diverge from the name and does not appear in a listing. The suffix states the type without opening the file and lets editors choose the schema |
| no inheritance between profiles in 1.0 (`extends` reserved) | `base = "eastron/sdm630@1"` | a profile is read and reviewed on its own; model families are handled with the importer; inheritance complicates the lock and `jk profile diff` |
| a single conformance schema (D10), with `do`/`expect` and `at`, also for the drivers (ref/06 §6) | keep `[[ticks]]` in the core, `do`/`expect` in the classes and `[[steps]]` in the drivers | two vocabularies for the same thing; with `do`/`expect`, the literals and the predicates are the same in scenarios, core cases, class cases and driver cases. **Declared exception:** in `driver` suites, and only there, the instants accept the term `timeout` (the one of the fixture), because the same case runs against drivers with different timeouts and, in tier X, with the deadlines scaled |
| `equals` for the applied value, everywhere | `applied` in the core | the value of an output **is** the applied one; a single name |
| display form accepted as a synonym (`Bad(CommFailure)`) | only `snake_case` | what the CLI shows must be pasteable; the translation is total and `jk fmt` normalizes |
| sums of instants (`2m+1.2s`) only in the timeline | writing `121.2s` | readability of tests; outside the timeline, the rule of ref/00 stands |
| the class package has no version | versioning the package and the classes | the class already has a version and a contract hash; a second version would only create conflicts |
| one OCI artifact per class version | one artifact per package | the lock and the compatibility are per class (17 §9) |
| the digest of profiles and boards in the lock is that of the file | that of the OCI manifest | it is the same for a local file and for the published one |
| versioned boards (`version`, `rpi5@1`) | boards without a version | a board also changes (a `/dev` path, a partition) and the lock must pin it |
| `fallback` on the IO lines of the board, instead of `safe` | `safe` (05 §11) | `safe` belongs to the manifest (ADR 0006); what the board knows is what the hardware does by itself, which is a fallback (M1) |
| `momentary` as a pulse | "while pressed" | impossible in a terminal (S11) |
| `health = "failed"` on instances, in scenarios | reading the quality of the members one by one | health belongs to the class (17 §4.5); the test should use the same rule |

## 8. Compatibility of `schema = 1` with the examples

- **Syntactically compatible.** No catalog or test file of the examples used a `schema` key at the root, nor a root key before the first table; adding `schema = 1` at the top gave valid TOML in all of them.
- **Applied (D11, finding A1).** The complete catalog and test files of the examples, of the track and of documents 04, 05, 14 and 16 now open with `schema = 1` (after the comment with the path). The excerpts marked "add" or "excerpt" do not repeat it, because they are not whole files.
- **"First key/value pair"** (ref/00 §1, D11): the examples open with a comment with the path (`# sim/tank.sim.toml`), and that is allowed; `schema = 1` comes right after.
